# 현대 웹 인프라 리스크

## React / Next.js RSC 원격 코드 실행 취약점
### 어떤 사건인가?
- React 서버 컴포넌트(RSC)에서 **원격 코드 실행(RCE)** 취약점 발견
- React, Next.js, Vite, RedwoodJS 등 **RSC 기반 생태계 전체 영향**
- 클라우드 환경 조사 결과, 스캔 대상의 상당 비율이 취약 버전 포함

### 왜 발생했나?
- RSC가 사용하는 **Flight 프로토콜 payload 역직렬화 로직**에 결함
- 객체 구조 검증이 부족해, 공격자가 조작한 payload → 서버 내부에서 코드처럼 실행 가능
- 개발자가 직접 작성하지 않은, **프레임워크가 자동으로 만든 서버 엔드포인트**가 취약
- App Router + Server Components 활성화만으로 취약 경로 노출 가능

### 여파
- 인증 없이, 단일 HTTP 요청으로 RCE 성립 가능
  - 서버 파일 읽기, 환경 변수/DB 비밀정보 탈취, 추가 악성 코드 설치 가능
- 취약점 공개 후 PoC, 공격 기법이 빠르게 공유
- 추가로, WAF 벤더(예: Cloudflare)가 긴급 룰 적용 중 자체 장애를 일으켜
  - 주요 서비스(LinkedIn, Zoom 등) 대규모 장애로 이어지는 2차 영향 발생

### 어떻게 해결·대응해야 하나?
- **즉각 패치**
  - React 서버 패키지: 취약 버전 → 최신 패치 버전 적용
  - Next.js: 각 메이저/마이너별 보안 패치 버전 적용
- **영향 범위 파악**
  - App Router, Server Actions, RSC 사용 여부 및 노출 경로 인벤토리화
- **사후 조치**
  - WAF/서버 로그 분석으로 공격 시도 여부 확인
  - 노출 가능성이 있는 비밀정보(토큰, API 키, DB 계정) 로테이션
- **교훈**
  - “프레임워크가 자동으로 해주는 서버 기능”도 위협 모델링 대상
  - 편의를 위해 도입한 기능 → 보안 면에서 어떤 공격 표면을 늘리는지 확인 필요

## AWS 대규모 장애
### 어떤 사건인가?
- 특정 시점에 AWS 한 리전(us-east-1) 장애로
  - 전 세계 수많은 서비스 동시 장애
  - 슬랙, 여러 SaaS, 일부 결제 서비스 등 일상 서비스 다수 영향
- 장애 시간은 수 시간 이상 지속, 막대한 경제적 손실 추산

### 왜 발생했나?
- 시작점: **DynamoDB 관련 DNS 해상(resolution) 문제**
- 핵심 인프라의 설정/자동화 소프트웨어 버그로 잘못된 구성이 배포
- 이 문제가 인증, 라우팅, 스토리지 등 내부 서비스에 **연쇄 전파(cascading failure)**

### 여파 & 이후 움직임
- us-east-1에 강하게 의존하던 서비스들이 한 번에 다운
- “클라우드 한 리전에 지나치게 집중된 아키텍처” 리스크가 현실로 드러남
- 이후 멀티 리전/멀티 클라우드 필요성에 대한 논의와 서비스(멀티클라우드 링크 등) 등장

### 어떻게 해결·대응해야 하나?
- **장애 격리 설계**
  - 최소한 읽기 트래픽은 다른 리전/클러스터에서 처리 가능하도록 구조 분리
- **핵심 기능의 백업 플랜**
  - 인증, 결제, 알림, 상태 페이지 등 핵심 기능에 대한 대체 루트/축소 모드 설계
- **자동화 시스템에 대한 신뢰 재점검**
  - IaC, 자동화 배포, 운영 스크립트 버그가 “전체 인프라 장애”로 이어질 수 있음을 전제
  - 카나리 배포, 점진 롤아웃, 빠른 롤백 전략 필수

## 왜 이런 일들이 계속 터지나?
1. **편의를 위해 복잡도가 폭증한 구조**
   - RSC, Server Actions, 자동 서버 렌더링
   - 거대 클라우드 내부의 수많은 자동화 서비스 연쇄 의존
2. **입력과 코드/구성 사이의 경계가 얇음**
   - RSC Flight payload → 역직렬화 → 코드 실행
   - 설정/자동화 값 → 곧바로 DNS/인프라 구성에 반영
3. **소수 벤더/리전에 대한 과도한 집중**
   - React/Next 생태계에 동일 취약점이 일괄 전파
   - 다수 서비스가 같은 리전(us-east-1)·같은 벤더(AWS, WAF)에 의존

> 결론적으로, “편의성과 효율성 중심 설계”가  
> **보안(취약점) + 가용성(대규모 장애)** 측면에서 얼마나 큰 리스크를 만드는지 보여주는 사례들

## 우리는 어떻게 대응해야 하나?
1. **우리는 어떤 프레임워크/벤더에 얼마나 의존하고 있는가?**
   - React/Next, Spring, AWS, Cloudflare 등
   - 이 중 하나가 오늘 밤 장애 나면, 우리 서비스는 어디까지 영향을 받는가?
2. **편의를 위해 도입한 기능이 늘린 공격 표면을 이해하고 있는가?**
   - RSC, Server Actions, 자동화 배포, IaC, 멀티테넌시 등
3. **단일 장애 지점(Single Point of Failure)을 줄이기 위한 설계가 되어 있는가?**
   - 멀티 리전, 멀티 벤더, 기능 축소 모드(Degraded Mode), 상태 페이지 등
4. **보안 패치와 인프라 변경이 “배포 프로세스”로 관리되고 있는가?**
   - 카나리/블루그린/롤백 전략 적용 여부
   - 보안 패치도 결국은 배포라는 인식 공유
5. **프론트/백엔드가 함께 논의해야 할 지점은 무엇인가?**
   - 장애/보안 이슈 시 UX (오류 메시지, 상태 페이지, 재시도 전략)
   - 에러 코드/타임아웃 정책/재시도 정책 등 공통 규칙
