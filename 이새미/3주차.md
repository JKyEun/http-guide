## 5장 웹 서버

- 여러 종류의 소프트웨어 및 하드웨어 웹 서버에 대해 조사한다.
- HTTP 통신을 진단해주는 간닪나 웹서버를 펄(Perl)로 작성해본다.
- 어떻게 웹 서버가 HTTP 트랜잭션을 처리하는지 단계별로 설명한다.

**5.1 다채로운 웹 서버**

- 웹 서버는 기능, 형태, 크기가 다양하다. 모든 웹 서버는 리소스에 대한 HTTP 요청을 받아서 콘텐츠를 클라이언트에게 돌려준다.

**5.1.1 웹 서버 구현**

- 웹 서버는 HTTP 프로토콜 구현, 웹 리소스/ 서버 관리 기능 제공, TCP 커넥션 관리에 대한 책임을 운영체제와 나눠 갖는다.
- 운영체제는 컴퓨터 시스템의 하드웨어 관리, TCP/IP 네트워크 지원, 웹 리소스를 유지하기 위한 파일 시스템, 현재 연산 활동을 제어하기 위한 프로세스 관리 제공

**5.1.2 다목적 소프트웨어 웹 서버**

- 다목적 소트프웨어 웹 서버는 네트워크에 연결된 표준 컴퓨터 시스템에서 동작한다.
- 아파치, W3C, 직소, 마이크로소프트, 아이플래닛

**5.1.3 임베디드 웹 서버**

- 일반 소비자용 제품(프린터나 가전제품)에 내장될 목적으로 만들어진 작은 웹 서버이다.
- 보통 최소한의 기능만 제공

**5.2 간단한 펄 웹 서버**

HTTP 커넥션 대기,

요청 메시지를 받은 후 화면에 출력

클라이언트에게 답해줄 응답 메시지를 타이핑 대기

HTTP 요청 메시지를 정확하게 기록하고 어떤 HTTP 응답 메시지라도 돌려보내줄 수 있도록 하는 최소한의 기능 구현

- HTTP 커넥션을 기다린다.
- 요청 메시지를 받는다.
- 화면에 메시지를 출력한다.
- 클라이언트에게 답해줄 응답 메세지를 타이핑하기를 기다린다.

→ HTTP 요청 메시지를 정확하게 기록하고 어떤 HTTP 응답메시지라도 돌려보내줄 수 있도록 해준다.

**5.3 진짜 웹 서버가 하는 일**

1. 커넥션을 맺는다 - 클라이언트의 접속을 수용하거나, 원치 않는 클라이언트라면 닫는다.
2. 요청을 받는다 - HTTP 요청 메시지를 네트워크로부터 읽어 들인다.
3. 요청을 처리한다 - 요청 메시지를 해석하고 행동을 취한다.
4. 리소스에 접근한다 - 메시지에서 지정한 리소스에 접근한다.
5. 응답을 만든다 - 올바른 헤더를 포함한 HTTP 응답 메시지를 생성한다.
6. 응답을 보낸다 - 응답을 클라이언트에게 보낸다.
7. 트랜잭션 로그로 남긴다. - 로그 파일에 트랜잭션 완료에 대한 기록을 남긴다.

**5.4 단계 1: 클라이언트 커넥션 수락**

- 클라이언트가 이미 서버에 대해 열려있는 지속적 커넥션을 갖고 있다면, 클라이언트는 요청을 보내기 위해 그 커넥션을 사용할 수 있다. 그렇지 않다면 클라이언트는 서버에 대한 새 커넥션을 열 필요가 있다.

**5.4.1 새 커넥션 다루기**

- 클라이언트가 웹 서버에 TCP 커넥션을 요청 → 웹 서버는 그 커넥션을 맺음 → TCP 커넥션에서 IP주소를 추출하여 커넥션 맞은편에 어떤 클라이언트가 있는지 확인 → 서버는 새 커넥션을 목록에 추가하고 커넥션에서 오가는 데이터를 지켜보기 위한 준비
- 웹 서버는 어떤 커넥션이든 마음대로 거절하거나 즉시 닫을 수 있다.

**5.4.2 클라이언트 호스트 명 식별**

- 대부분의 웹 서버는 역방향 DNS(reverse DNS)를 사용해서 클라이언트의 IP 주소를 클라이언트의 호스트 명으로 변환하도록 설정되어 있다.
- 웹 서버는 이 호스트 명을 구체적인 접근 제어와 로깅을 위해 사용할 수 있다.

**5.4.3 ident를 통해 클라이언트 사용자 알아내기**

- 몇몇 웹 서버는 또한 IETF ident 프로토콜을 지원한다. ident 프로토콜은 서버에게 어떤 사용자의 이름이 HTTP커넥션을 초기화했는지 찾아낼 수 있게 해준다.
  → 웹 서버 로깅에서 유용
- 만약 클라이언트가 ident 프로토콜을 지원한다면, 클라이언트는 ident 결과를 위해 TCP 포트 113번을 listen한다.
- 커넥션이 맺어진 후 서버는 새 커넥션(클라이언트와 서버 포트 번호로 지정되는)에 대응하는 사용자 이름을 묻는 요청을 보낸다.

**5.5 단계 2: 요청 메시지 수신**

커넥션에 데이터가 도착하면, 웹 서버는 네트워크 커넥션에서 그 데이터를 읽어들이고 파싱하고 요청 메시지를 구성한다.

- 요청 메시지를 파싱할 때, 웹 서버는 입력 데이터를 네트워크로부터 불규칙적으로 받는다.
- 네트워크 커넥션은 언제라도 무효화될 수 있다.
- 웹 서버는 파싱해서 이해하는 것이 가능한 수준의 분량을 확보할 때까지 데이터를 네트워크로부터 읽어서 메시지 일부분을 메모리에 임시로 저장해 둘 필요가 있다.

**5.5.1 메시지의 내부표현**

- 몇 웹 서버는 요청 메시지를 쉽게 다룰 수 있도록 내부 자료구조에 저장하여 효율적 접근이 가능하도록 함

**5.5.2 커넥션 입력/출력 처리 아키텍처**

요청은 언제라도 올 수 있기 때문에 웹 서버는 항상 새 요청을 주시하고 있다.

**단일 스레드 웹 서버**

- 웹 서버는 한 번에 하나씩 요청을 처리한다.
- 트랜잭션이 완료 되면 다음 커넥션 처리
- 처리 도중 다른 요청은 무시하기 때문에 성능 문제가 있다.
- 로드가 적은 서버나 진단도구에서만 적합함

**멀티프로세스와 멀티스레드 웹 서버**

- 여러 요청을 동시에 처리하기 위해 여러개의 프로세스 혹은 고효율 스레드를 할당한다.
- 스레드/프로세스는 미리 만들어질 수도 있고 필요할 때 만들어질 수도 있다.
- 몇몇 서버는 매 커넥션 마다 스레드/프로세스를 만들어내지만 수천, 수만개의 커넥션을 동시에 처리하기 위해 만들어진 스레드/프로세스로 인해 너무 많은 메모리나 시스템 리소스를 소비할 수 있어 최대 스레드/프로세스 수를 제한이 필요함

**다중 I/O서버**

- 다중 아키텍처에서는 모든 커텍넥은 동시에 그 활동을 감시당한다.
- 커넥션의 상태가 바뀌면(데이터를 사용할 수 있게 되거나 에러가 나게되면), 그 커넥션에 대해 작은 양의 처리가 수행되고 다음 커넥션의 상태를 위해 열린 커넥션 목록으로 들어감
- 어떤 커넥션에 대해 작업을 수행할 때는 실제로 그 커넥션에 대해 할 일이 있을 때이다. 프로세스와 스레드는 유휴상태인 커넥션을 위해 낭비되지 않는다.

**다중 멀티스레드 웹 서버**

- 멀티 스레딩과 다중화를 결합
- 여러 개의 스레드(보통 하나의 불리적 프로세스)는 각각 열려있는 커넥션(혹은 열려있는 커넥션의 부분집합)을 감시하고 각 커넥션에 대해 조금씩 작업을 수행한다.

**5.6 단계 3: 요청 처리**

- 웹 서버가 요청을 받으면, 서버는 요청으로부터 메서드, 리소스, 헤더, 본문을 얻어 처리한다.

**5.7 단계 4: 리소스의 매핑과 접근**

- 웹 서버는 리소스 서버다.
- HTML, JPEG같은 미리 만들어진 정적 콘텐츠를 제공하기도 하고, 서버 위에서 동작하는 리소스 생성 애플리케이션을 통해 만들어진 동적 콘텐츠를 제공하기도 한다.

**5.7.1 Docroot**

- 리소스 매핑의 가장 단순한 형태는 요청 URI를 웹 서버의 파일 시스템 안에 있는 파일 이름으로 사용하는 것이다.
- 일반적으로 웹 서버 파일 시스템의 특별한 폴더를 웹 콘텐츠를 위해 예약해 둔다. 이 폴더 문서는 루트 혹은 docroot로 불린다.
- 웹 서버는 요청 메시지에서 URI를 가져와 문서 루트 뒤에 붙인다.
- 서버는 상대 주소가 docroot를 벗어난 경로에 접근되어 의도되지 않은 리소스가 노출되지 않도록 해야한다.

**가상 호스팅된 docroot**

- 가상 호스팅 웹 서버는, 하나의 웹 서버에 분리된 문서 루트를 설정하여 여러 개의 웹 사이트가 서빙될 수 있도록 할 수 있다.

**사용자 홈 디렉터리 docroots**

- 사용자 웹 서버에서 웹 사이트를 만들 수 있도록 해주는 것
- 보통 빗금(/)과 물결표(~) 다음에 사용자 일므이 오는 것으로 시작하는 URI는 그 사용자의 개인 문서 루트를 가리킨다.
- 개인 docroot는 주로 사용자 홈 디렉터리 안에 있는 public_html로 불리는 디렉터리지만, 설정에 따라 다르다.

**5.7.2 디렉터리 목록**

- 웹 서버는, 경로가 파일이 아닌 디렉터리를 가리키는, 디렉터리 URL에 대한 요청을 받을 수 있다. ( ex) 해당 디렉토리에 index 파일을 찾아 응답)
- 클라이언트가 디렉터리 경로를 요청했을 때 서버에서 다음과 같은 행동을 취하도록 설정할 수 있음
  - 에러 반환
  - 디렉터리 대신 특별한 ‘색인 파일’을 반환
  - 디렉터리를 탐색해서 그 내용을 담은 HTML 페이지를 반환
- 대부분은 해당 디렉토리 안에서 index.html, index.htm 파일을 반환

**5.7.3 동적 콘텐츠 리소스 매핑**

- 웹 서버는 URI를 동적 리소스에 매핑할 수 있다.
- 요청에 맞게 콘텐츠를 생성하는 프로그램에 URI를 매핑하는 것
- 웹 서버들 중에서 애플리케이션 서버라고 불리는 것은 웹 서버를 복잡한 백엔드 애플리케이션과 연결하는 일을 한다.
- 어떤 리소스가 동적 리소스라면, 애플리케이션 서버는 그에 대한 동적 생성 프로그램이 어디에 있는지, 어떻게 실행하는지 알려줄 수 있어야함

**5.7.4 서버사이드 인클루드(Server-Side Includes, SSI)**

- 만약 어떤 리소스가 서버사이드 인클루도를 포함하고 있는 것으로 설정되었다면, 서버는 그 리소스의 콘텐츠를 클라이언트에게 보내기 전에 처리한다.
- 서버는 콘텐츠에 변수 이름이나 내장된 스크립트가 될 수 있는 특별한 패턴이 있는지 검사 > 실행가능한 출력 값으로 치환 > 동적 콘텐츠 생성

**5.7.5 접근 제어**

- 웹 서버는 각각의 요청에 대해 접근 제한을 할 수 있다.
- 접근 제어되는 리소스에 대한 요청이 도착했을 때 클라이언트 IP를 확인해서 접근을 제한할 수도 있고 비밀번호를 요청할 수도 있다.

**5.8 단계 5: 응답 만들기**

한번 서버가 리소스를 식별하면 요청 메소드로 서술되는 동작을 처리를한 후 응답 메세지를 반환한다.

**5.8.1 응답 엔터티**

- 만약 트랜잭션이 응답 본문을 생성한다면, 그 내용을 응답 메시지와 함께 돌래보낸다.

**5.8.2 MIME 타입 결정하기**

- 웹 서버에게는 MIME타입을 결정해야하는 책임이 있다.
- 리소스와 MIME 타입을 연결하는 방법
  - mime.types
    - 파일 이름의 확장자를 사용
    - 확장자별 MIME 타입이 담겨 있는 파일을 탐색
  - 매직 타이핑
    - 표준 확장자 없이 이름 지어진 경우 파일의 내용을 검사해서 알려진 패턴에 대한 테이블에 해당 하는 패턴이 있는지 찾기
  - 유형 명시
    - 특정 파일이나 디렉터리 안의 파일들이 파일 확장자나 내용에 상관 없이 특정한 MIME 타입을 갖도록 웹 서버를 설정할 수 있음
  - 유형 협상
    - 웹 서버는 하나의 리소스가 여러개의 문서 형식에 속하도록 설정할 수 있다.
    - 웹 서버가 사용자와의 협상 과정을 통해 사용작가 사용하기 가장 좋은 형식과 이에 대응하는 MIME 타입을 판별할 것인지 여부도 설정할 수 있다.

**5.8.3 리다이렉션**

- 웹 서버는 요청을 수행하기 위해 브라우저가 다른 곳으로 가도록 리다이렉트할 수 있다.
- 성공 메시지 대신 리다이렉트 응답을 반환한다.
- 상태코드는 3XX, Location 응답 해더로 URI 포함
- 유용한 경우
  - 영구히 리소스가 옮겨진 경우
    - 301 Moved Permanently 상태코드 사용
  - 임시로 리소스가 옮겨진 경우
    - 303 See Otherr, 307 Temporary Redirect 상태코드 사용
    - 임시적이기 때문에 클라이언트가 나중에 원래 URL로 찾아오도록 해야함
  - URL 증강
    - 문맥 정보를 포함시켜 트랜잭션간 상태를 유지하는 방법
    - 서버 : 클라이언트로 부터 요청 도착 → 상태 정보를 포함한 새 URL 생성 → 클라이언트 전송
    - 사용자: 새 URL로 리다이렉트 → 상태정보가 추가된 완전한 URL을 포함한 요청
    - 303 See Otherr, 307 Temporary Redirect 상태코드 사용
  - 부하 균형
    - 과부하 된 서버로 요청이 온 경우, 부하가 덜 일어난 서버로 리다이렉트
    - 303 See Otherr, 307 Temporary Redirect 상태코드 사용
  - 친밀한 다른 서버가 있을 때
    - 사용자의 정보를 가진 다른 서버로 리다이렉트
    - 303 See Otherr, 307 Temporary Redirect 상태코드 사용
  - 디렉터리 이름 정규화
    - 클라이언트가 디렉터리 이름에 대한 URI 요청을 하는데 빗금을 빠뜨렸다면 슬래시를 추가한 URI로 리다이렉트

→ 브라우저 주소창에서 발생한 네트워크 요청이라면, 브라우저가 3xx 응답에 대해 자동으로 리다이렉트, 앱 코드의 의도, 스크립트 여부와 무관하게 작동

→ Fetch 등을 통한 api요청을 통해 3XX 응답을 받은 경우에는 브라우저가 페이지를 이동시키지 않는다.

**브라우저는 “페이지 이동”을 하지 않는다**

- 주소창 URL은 그대로
- 렌더된 앱 UI도 그대로
- 라우터 전환 없음

**내부적으로는 “리다이렉트 따라갈지 여부”만 처리**

fetch의 기본 동작은 redirect: "follow"

→ 브라우저 내부적으로 리다이렉트 요청을 다시 보낸 뒤 결과만 fetch로 돌려줌.

→ 최종적으로 JS에서 받는 응답은 **리다이렉트 후의 응답**이다.

**5.9 단계 6: 응답 보내기**

- 서버는 커넥션 상태를 추적해야하며 지속적인 커넥션은 특별히 주의해서 다룰 필요가 있다.
- 비지속적 커넥션 - 서버는 모든 메세지를 전송했을 때 커넥션을 닫을 것
- 지속적 커넥션 - 서버가 Content-Length를 올바르게 계산하기 위해 특별한 주의를 필요로하는 경우나 클라이언트가 응답이 언제 끝날지 모르는 경우 커넥션은 열린 상태를 유지할 것

**5.10 단계 7: 로깅**

- 웹 서버는 트랜잭션이 끝났을 때 어떻게 트랜잭션이 어떠헤 수행됐는지 로그를 로그파일에 기록한다.
