## 9.1. 크롤러와 크롤링
- 왜? 크롤러, 크롤링인가 -> 수많은 웹들을 끝없이 따라가면서 기어디니기 (Crawl) 때문

### 9.1.1 루트 집합
- 굶주린 크롤러는 루트 집합(URL 집합)에서 출발 한다.
- 웹들은 연결되어 있기에, 루트 집합이 너무 많을 필욘 없다.
- 좋은 루트 집합
  - 크고 인기 있는 웹 사이트
  - 새로 생성된 페이지
  - 자주 링크되지 않는 잘 열려있지 않은 사이트
- 대규모 크롤러 제품은 사용자들이 루트 집합에 새로운 페이지를 추가하는 기능을 제공

### 9.1.2 링크 추출과 상대 링크 정상화
- 크롤러들이 탐험을 하면서 찾은 상대 링크를 절대 링크화 해야한다. 
  - 왜? 
    - 상대 링크는 현재 페이지의 URL을 기준으로 한다.
    - 상대 링크를 절대 링크로 변환하지 않으면, 다른 페이지의 링크를 찾을 수 없다.

### 9.1.3 루프의 발생
- 링크를 추출하면서 순환을 피해야한다. (중요)
  - ex)
    - A -> B -> C -> A
    - A -> B -> C -> A -> B -> C -> 
      => 이렇듯, 순환을 피해야한다. => 느려진다. => 어디를 방문했는지 알아야 한다.

### 9.1.4 루프와 중복
- 루프의 해로운 점
  - 꼼짝 못하게 함
  - 반복 작업으로 웹 서버에 부담
  - 자칫하면, 똑같은 결과들을 크롤러가 가지게 됨

### 9.1.5 빵 부스러기의 흔적
- 수십억개, (2025년 기준? : 구글 검색 색인 약 4,000억 개 : Gemini 검색 피셜 11억개의 도메인 X 인덱싱 대상)
- 수천억개 -> 검색 트리 or 해시 테이블 구조의 인덱스 필요
- URL당 40 바이트 공간 -> 40 X 4,000억 = 약 160TB
  => 이렇듯 크롤러가 제대로 동작하기 위해서 기법이 필요
- 트리, 해시 테이블 : 빨리 찾게 도와줌
- 느슨한 존재 비트맵 : 각 URL당 해당 되는 존재 비트 저장 -> 중복 방지
  - 왜 느슨하다고 표현 하는지? 
    - 충돌 가능성 (False Positive) : 해시 함수를 사용하기 때문에 서로 다른 URL이 같은 비트에 매핑될 수 있음.
    - 즉, "방문하지 않았는데 방문했다"고 착각할 수 있는 "느슨함"을 허용하는 대신, 메모리 공간을 획기적으로 줄이는 트레이드 오프를 가짐.
- 체크포인트 : 중단 -> 다시 시작시 어디 까지 했는지 저장
- 파티셔닝 : 하나의 봇으로는 불가능 -> 각각 분리(Partitioning)된 한대의 컴퓨터인 로봇들이 동시에 농장(Farm)에서 일함 -> 각 로봇엔 URL들의 특정 부분을 할당

### 9.1.6 별칭(alias)과 루프
- 다른 URL 들이 같은 리소스를 가리키게 됨
  - ex) 
    - http://www.foo.com/ -> http://foo.com/  
    - http://www.foo.com/-> http://www.foo.com/index.html

-> 이전에 방문했는지 확인 쉽지 않음

### 9.1.7 URL 정규화
- URL 정규화 : URL을 표준화하는 과정
  - ex) 
    - 포트 명시 X -> 호스트명에 포트번호 포함
    - `#`태그를 제거 
    - 모든 %이스케이프 문자 -> 대응 문자로 변환
- But, 정규화로 모든 URL이 표준화 되지 않음

### 9.1.8 파일 시스템의 링크 루프
- 심벌릭 링크 : 파일 시스템의 링크 (바로가기 같은 개념)
  - Next.js의 `@/app`은 빌드 타임 별칭(Alias)이지, OS 레벨의 심벌릭 링크가 아님.
  - 심벌릭 링크 루프 예시:
    - `subdir/` 안에 `root/`로 가는 심벌릭 링크가 있다면?
    - `subdir/subdir/subdir/subdir/subdir/...` 무한 루프 발생 가능

### 9.1.9 동적 가상 웹 공간
- 동적 콘텐츠, 심벌릭 링크 -> 크롤러 루프 함정을 만들 수 있음
  ex) 한달치 달력 생성 -> 그 다음달 링크 거는 CGI 기반 달력 
    - 크롤러가 무한히 다음달을 요청

### 9.1.10 루프와 중복 피하기
- 모든 루프는 완벽히 피할 수 없다.
- 휴리스틱한 크롤러 -> 피할 확률도 높지만, 그만큼 유효한 콘텐츠도 피할 확률도 높아진다.
- 앞서서 말했던 방법들을 포함해 루프를 피할 방법을 정리하자면
1. URL 정규화 : URL을 표준화하여 중복을 피할 수 있음
2. 너비 우선 크롤링(BFS) : 깊이 우선 크롤링(DFS)보다 루프를 피할 확률이 높음
3. 스로틀링 : 페이지 숫자 제한
4. URL 크기 제한 : 일정 길이 이상을 제한 -> 가져 오지 못하는 콘텐츠도 많아질 것
5. URL 블랙 리스트 : 특정 URL을 차단 
6. 패턴 발견 : 순환 패턴을 발견하고 중단
7. 콘텐츠 지문 : 콘텐츠에서 몇 바이트 얻어냄 -> 체크섬을 계산 (간략화)
8. 모니터링 : 사람이 크롤러 상황을 직접 모니터링

## 9.2. 로봇의 HTTP
- 로봇들은 대게 HTTP/1.0 요청을 보낸다.
- 현재 2025년 12월 기준으로는?
  - 과거 로봇들은 단순성을 이유로 HTTP/1.0 요청을 보내는 경우가 많았으나,
  - 2025년 기준 주요 검색 크롤러(Googlebot, Bingbot 등)와 AI 기반 크롤러(GPTBot 등)는
    HTTP/1.1 또는 HTTP/2를 기본적으로 사용한다.
  - HTTP/1.0을 사용하는 로봇은 대부분 구형 크롤러거나 비정상적인 스팸 봇에 가깝다.

### 9.2.1 요청 헤더 식별
- 특히 User-Agent 헤더를 통해 신원을 식별하고 전송
- User-Agent : 서버에게 요청을 만든 로봇의 이름을 말해줌.
- From : 로봇의 사용자/관리자의 이메일 주소를 제공한다.
- Accept : 어떤 미디어 타입을 보내도 되는지 말해줌.
- Referer : 요청을 만든 페이지의 URL을 제공한다.
### 9.2.2 가상 호스팅
- 서버에 2개(A,B)의 사이트가 운영되어있을 때 -> Host 헤더가 없다면 -> A에 대한 정보를 요청 -> B에 대한 정보를 제공
### 9.2.3 조건부 요청
- 로봇들은 버전에 따라 업데이트 된 것만을 조건부 요청할 수 있음 
### 9.2.4 응답 다루기
- 대다수 GET 메서드로 요청
- 상태 코드 (이전 발표 자료 내용)
  - **200:** HTML을 크롤하고 파싱합니다.
  - **30X:** 리디렉션을 따라갑니다.
  - **40X:** 오류를 기록하고 HTML은 불러오지 않습니다.
  - **50X:** 상태 코드가 변경되었는지 나중에 다시 확인할 수 있습니다.

  | HTTP Status Code | SEO와 관련성 |
  | --- | --- |
  | 200 | Google에서 페이지가 인덱싱되기 위해서는 반드시 200 상태 코드를 반환해야 한다. |
  | 301 / 308 | 리디렉션의 가장 큰 목적은 **URL이 A에서 B로 이동했음을 알리는 것**이다. 콘텐츠가 이동하더라도 현재 및 잠재 고객을 잃지 않도록 하고, 봇이 계속해서 사이트를 인덱싱할 수 있도록 하기 위해 리디렉션이 필요하다. |
  | 404 | 404 상태 코드가 무조건 나쁜 것은 아니다. 존재하지 않는 URL을 사용자가 방문했다면 그게 올바른 결과이다. 하지만 사이트 전체에서 잦은 404 발생은 검색 순위 하락으로 이어질 수 있으므로 주의해야 한다. |
  | **410** | 이 상태 코드는 자주 사용되지는 않지만, 더 이상 존재하지 않는 콘텐츠를 사이트에서 삭제할 때 고려할 수 있다 **HTTP 410을 사용하면 좋은 예**: **이커머스**: 영구적으로 품절되어 더는 판매하지 않는 제품, **포럼**: 사용자가 삭제한 게시글 , **블로그**: 삭제된 블로그 글, **이 상태 코드는 봇에게 이 콘텐츠는 다시는 크롤하지 말라는 신호를 준다.** |
  | **503** | 사이트가 다운되어 있고, **오랜 시간 동안 다운될 것으로 예상되는 경우**, 이 상태 코드를 반환하는 것을 추천한다.이렇게 하면 장기적인 검색 순위 하락을 방지할 수 있다. |

- 엔터티 
  - 엔터티 : HTTP 메시지의 실제 데이터(화물)를 의미. (최신 스펙에서는 'Representation(표현)'이라고 부름)
    - 구성: 엔터티 헤더(Content-Type, Length 등) + 엔터티 본문(실제 데이터)  - 로봇들이 HTTP 헤더를 통해 엔터티 자체의 정보를 찾을 수 있다.
- (현재 기준 설명) ```<meta http-equiv="refresh">```는 Googlebot을 포함한 주요 검색 엔진이 리다이렉션 신호로 인식할 수 있으나, SEO와 접근성 측면에서는 HTML 리디렉션을 찾으려면 HTML을 구문 분석해야 하기 때문에
서버 측 301/302 리다이렉션보다 안정성·명확성이 크게 떨어진다.

- 특히 1초 이상의 지연 리프레시는 일시적 이동으로 처리될 수 있으며,
W3C 접근성 기준에서도 비권장 기술로 분류된다.
2025년 현재의 웹 표준 및 검색 엔진 권장 사항 : 모든 실제 이동을 서버 측 301/302로 처리하고, meta refresh는 가능한 한 사용하지 않는 것이다.

### 9.2.5 User-Agent 타겟팅
- 브라우저 종류에 맞게 콘텐츠 최적화
  - 어떻게?
    - User-Agent 헤더를 사용하여 브라우저 종류를 식별
    - 브라우저 종류에 따라 다른 콘텐츠 제공 
  - 실제 사례 궁금
    - Facebook
      - 모바일 -> m.facebook.com
      - 데스크톱 -> www.facebook.com
    - 네이버 
      - 모바일 -> m.naver.com
      - 데스크톱 -> www.naver.com

을 강제 분기시켰다.


## 9.3. 부적절하게 동작하는 로봇
- 폭주하거나 호기심이 많은 로봇, 오래되고 길고 잘못된 URL
- 폭주 : 순환 -> 부하 -> 방지 필요
- 호기심 많음 : 사적 데이터에 대한 관심 -> 사생활 침해
- 오래된 URL : URL 목록이 오래됨 -> 존재 하지 않은 페이지에 대한 요청
- 길고 잘못된 URL : 대단히 길거나, 의미 없는 URL에 요청 가능 함(순환 등을 이유로) -> 웹 서버 처리 능력에 영향
- 동적 게이트웨이 접근 : 게이트웨이 어플리케이션의 콘텐츠에 대한 URL로 요청 -> 특수 목적일 테니까 -> 테고 비용 발생
  - ex) 결제 영수증(Invoice) 동적 생성 URL
    - Stripe, PayPal 등은 영수증을 정적 파일로 제공하지 않고, 다음처럼 게이트웨이를 통해 동적으로 생성된 페이지로 제공함:
    https://api.stripe.com/v1/receipts/invoice_8394hf93h4
    - 특징: 매 요청 시 서버 내부에서 권한 검사 → 템플릿 렌더링 → PDF/HTML 동적 생성 비용(light compute)이 발생하고, API rate-limit 적용

## 9.4. 로봇 차단하기
### 9.4.1 로봇 차단 표준
- 최초 Robots Exclusion Protocol(Robots.txt)로 정의됨 (비표준이지만 사실상 표준인 느낌, 아래 버전도 비슷한 느낌)
  
  | 버전 | 이름과 설명 | 날짜 |
  | --- | --- | --- |
  | 0.0 | 오리지널 robots.txt | 1994년 |
  | 1.0 | 0.0이 만들어지고 확장된 개념이 추가된 버전 | 1996년 |
  | 2.0 | 1.0이 만들어지고 확장된 개념이 추가된 버전 | 1996년 |

  - robots.txt는 1994년 이후 공식 RFC 표준이 없었다가, IETF에서 robots.txt를 RFC로 정리한 시점은 2022년(RFC 9309). 오늘날까지도 ‘비공식·사실상 표준’로만 운영된다.
  - https://datatracker.ietf.org/doc/html/rfc9309?utm_source=chatgpt.com
  - `utm_source=chatgpt.com` : Google Analytics 계열에서 사용하는 트래픽 추적용 표준 파라미터
    - 예: ?utm_source=google&utm_medium=cpc&utm_campaign=spring_sale
    - utm_source : “이 유입이 어디서 왔는가?” (출처)
    - utm_medium : 유입 방식(organic, paid, email 등)
    - utm_campaign : 캠페인 이름
### 9.4.2 웹 사이트와 robots.txt 파일들
- GET을 통해서 가져옴
- 200 -> 규칙 따름
- 404 ->  제약 없이 접근한다.
- 401 혹은 403 -> 접근 완전 제한
- 503 -> 우선 순위를 미룬다.
- 3XX -> 리다이렉트 따라간다.
### 9.4.3 robots.txt 파일 포맷
- `필드 : 값` 형태의 줄로 구성

| 필드 | 설명 |
| --- | --- |
| User-agent | 로봇 이름 |
| Allow | 허용된 URL |
| Disallow | 허용되지 않은 URL |

### 9.4.5 robots.txt 캐싱과 만료
- HTTP 캐시 제어 매커니즘이 서버와 로봇 양 쪽에서 모두 사용됨
- 초안은 일주일간 캐싱 -> 너무 길다.
### 9.4.7 META 태그  
- robots.txt와는 다르게 HTML 문서 내부에 포함
- 모든 로봇 meta 태그는 `name="robots"`로 설정

## 9.5. 로봇 에티켓
- 신원 :  로봇,기계(로봇의 책임 위치)의 신원과 연락처
- 동작 : 조심하고 신중해라 항상 대비하고 문제 있다면 개선
- 제한 : URL 필터링, HTTP Accept 헤더 필터링, robots.txt, 너무 자주 방문치 않도록
- 루프와 중복 : 응답 코드 대응, URL 정규화, 적극적 루프 피하기, 함정 감시, 블랙리스트 관리
- 확장 : 공간, 대역폭, 시간 이해, 분할 전략
- 신뢰 : 테스트, 체크포인트, 유연성
- 소통 : 준비, 이해, 대응

- 참고) 웹 마스터 : 특정 사이트의 주인 + 관리자 + 기술 담당자 역할을 모두 포함하는 이름

## 9.6. 검색엔진
- 크롤러는 검색엔진에게 먹이(문서)를 주는 역할을 한다.
- 먹이를 받은 검색엔진은 먹이를 분석하고 인덱스를 만든다.

### 9.6.1 넓게 생각해라
- 단순 -> 복잡 : 검색엔진의 아키텍처가 복잡해짐 -> 넓게 생각해라?
### 9.6.2 현대 검색엔진 아키텍처
- 검새엔진은 full-text indexes라는 데이터 베이스를 생성한다
-  현대 검색엔진은 더 이상 단순한 full-text 인덱스(역색인)만을 사용하지 않는다.
대표적인 오픈소스 검색엔진들은 기존의 키워드 기반 역색인 방식에 더해,
embedding 기반 벡터 인덱스(vector index) 를 함께 운용하며 이 인덱스를 통해 검색엔진은 키워드를 넘어 의미를 이해하고,
LLM과 결합하여 요약된 답변을 생성할 수 있게 되었다.

### 9.6.3.1 풀 텍스트 인덱스
- `단어 하나 -> 모든 포함 문서` 알 수 있는 DB
### 9.6.3.2 벡터 인덱스
- 텍스트·이미지·오디오 같은 데이터를 임베딩(embedding) 벡터로 변환한 뒤,
그 벡터들 사이의 “의미적 유사도”를 빠르게 검색하기 위해 구성된 특수 인덱스 구조이다.

### 9.6.5 검색 결과를 정렬하고 보여주기
- 랭킹에 따라 순서를 정렬하고, 검색 결과를 보여준다.
- 검색엔진에 의해 사용되는 알고리즘 등등 방법은 다양하다.

### 9.6.6 스푸핑
- 검색엔진은 스푸핑을 방지하기 위해 여러가지 방법을 사용한다.
- 스푸핑 : 검색엔진을 이용하여 자신의 웹사이트를 노출시키는 방법 (예: 스크레이퍼, 봇)

  ## 10.1 HTTP/2.0의 등장 배경
  - 책에서는 HTTP/2.0 의 8번째 초안에 기반하여 제작되었음
  - **2025년 현재 기준**:
    - 2015년 5월, **RFC 7540**으로 공식 표준화됨. https://httpwg.org/specs/rfc7540.html
    - 이후 2022년 6월, **RFC 9113**이 발표되면서 RFC 7540을 대체(Obsolete)하고 현재의 공식 표준이 됨. https://httpwg.org/specs/rfc9113.html
    - 주요 변경점: 우선순위 지정(Priority) 방식이 복잡하여 잘 쓰이지 않아 폐기(Deprecated)되고, 명세의 오류 수정 및 명확화가 이루어짐.
  - HTTP/1.1 성능 이슈 : 응답을 받아야만 다음 요청을 할 수 있었다. -> 심각한 회전 지연 이슈 
    - -> HTTP-NG, WAKA, Microsoft S+M 프로토콜을 개발하기 시작함, 프로토콜을 내놓음
    - 구글은 SPDY 프로토콜을 내놓음
      - SPDY : 헤더 압축 -> 대역폭 절약, 하나의 TCP 커넥션으로 여러개의 HTTP 동시 요청을 할 수 있도록 함
  ## 10.2 HTTP/2.0의 개요
  - HTTP/1.1의 메시지 전송 방식에 변화를 주어 성능을 향상시킨 프로토콜.
  - 기존 HTTP/1.1의 의미(Method, Status Code, Header 등)는 그대로 유지하면서, 데이터 전송 방식만 바이너리 프레이밍 계층으로 변경함.
  - 핵심 목표: 지연 시간(Latency) 감소, 처리량(Throughput) 증대.

  ## 10.3 HTTP/1.1과의 차이점
  ### 10.3.1 프레임 차이
  - **HTTP/1.1**: 텍스트 기반(Text-based). 줄바꿈(\n)으로 데이터를 구분. 사람이 읽기 쉽지만 기계가 파싱하기엔 비효율적.
  - **HTTP/2.0**: 바이너리 프레임(Binary Frame) 단위로 전송.
    - 메시지를 '프레임'이라는 작은 단위로 쪼개서 전송.
    - 파싱 속도가 빠르고 오류 발생 가능성이 낮음.

  ### 10.3.2 스트림과 멀티플렉싱
  - **HTTP/1.1**: 요청을 순차적으로 처리(Pipelining이 있어도 HOL Blocking 문제 존재). 하나의 TCP 연결에서 한 번에 하나의 요청/응답만 처리 가능.
  - **HTTP/2.0**: 멀티플렉싱(Multiplexing) 지원.
    - **스트림(Stream)**: 가상의 양방향 데이터 흐름. 하나의 TCP 연결 내에서 여러 개의 스트림이 동시에 존재.
    - 하나의 연결로 여러 요청과 응답을 뒤섞어서(Interleaving) 동시에 전송 가능.
    - HOL(Head-of-Line) Blocking 문제 해결 (애플리케이션 계층에서).

  ### 10.3.3 헤더 압축 (HPACK)
  - **HTTP/1.1**: 매 요청마다 중복된 헤더(User-Agent, Cookie 등)를 텍스트로 계속 보냄 -> 대역폭 낭비.
  - **HTTP/2.0**: **HPACK** 알고리즘을 사용하여 헤더를 압축.
    - 정적/동적 테이블을 사용하여 중복된 헤더는 인덱스만 전송.
    - 허프만 인코딩으로 데이터 크기 감소.

  ### 10.3.4 서버 푸시 (Server Push)
  - **개념**: 클라이언트가 요청하지 않아도 서버가 미리 리소스(CSS, JS, 이미지 등)를 보내주는 기능.
  - **2025년 현재 기준**: **사실상 폐기됨 (Deprecated/Removed)**.
    - https://developer.chrome.com/blog/removing-push?utm_source=chatgpt.com&hl=ko
    - Chrome(106 버전부터), Firefox 등 주요 브라우저에서 지원 중단 및 제거됨.
    - 이유: 구현의 복잡성, 캐시 문제(이미 있는 것도 보내서 대역폭 낭비), 성능 이득이 불분명함. 사용하는 사이트는 1.25% 정도.
    - 대안: `<link rel="preload">` 또는 **103 Early Hints** 사용 권장.

  ### 10.3.5 요약
  | 특징 | HTTP/1.1 | HTTP/2.0 |
  | :--- | :--- | :--- |
  | 전송 포맷 | 텍스트 (Text) | 바이너리 (Binary) |
  | 다중화 | 불가 (Pipelining 제한적) | **멀티플렉싱 (Multiplexing)** 지원 |
  | 헤더 압축 | 미지원 | **HPACK** 지원 |
  | 우선순위 | 미지원 | 스트림 우선순위 (RFC 9113에서 단순화됨) |
  | 통신 방향 | 단방향 (요청 -> 응답) | 양방향 (서버 푸시 등, 단 푸시는 사장됨) |
  
  ## 10.4 알려진 보안 이슈와 현재 (2025년 기준)
  ### 10.4.1 Intermediary Encapuslation Attacks (중개자 캡슐화 공격)
  - **개념**: HTTP/2 메시지를 HTTP/1.1로 변환하는 중개자(Proxy, Gateway)의 취약점을 이용한 공격.
  - **원리**: 
    - HTTP/2는 헤더 필드의 길이와 값에 대한 검증이 엄격하지만, 이를 HTTP/1.1로 변환하는 과정에서 중개자가 제대로 검증하지 않으면 문제가 발생.
    - 공격자가 HTTP/2 헤더에 불법적인 문자(예: 개행 문자)를 숨겨서 보내면, 중개자가 이를 HTTP/1.1로 변환할 때 **HTTP Response Splitting**이나 **Request Smuggling** 공격으로 이어질 수 있음.
    - 특히 **H2C Smuggling**: 암호화되지 않은 HTTP/2(h2c) 업그레이드 메커니즘을 악용하여 프록시 보안 정책을 우회하고 백엔드 서버와 직접 통신하는 터널을 생성할 수 있음.

  ### 10.4.2 긴 커넥션 유지로 인한 개인정보 누출 우려
  - **개념**: HTTP/2는 성능을 위해 하나의 TCP 연결을 오랫동안 유지(Long-lived connection)하며 재사용함.
  - **위험성**:
    - **트래픽 분석(Traffic Analysis)**: 공격자가 암호화된 트래픽의 패턴(패킷 크기, 타이밍 등)을 분석하여 사용자가 어떤 페이지를 방문했는지 유추할 수 있음. (HTTP/2의 멀티플렉싱이 오히려 패턴을 복잡하게 만들어 분석을 어렵게 할 수도 있지만, 특정 조건에서는 여전히 취약함)
    - **크로스 도메인 추적 가능성**: 동일한 연결을 여러 도메인(같은 인증서/IP 사용 시)에서 재사용할 경우, 사용자의 이동 경로가 추적될 수 있는 이론적 가능성이 제기됨.
