## SEO가 왜 중요할까?

고깃집을 차린다고 해보자, 고깃집에선 사장, 손님을  떠올릴 수 있다.

그리고 ‘맛있는 고기 드세요’ 라는 광고를  유료 맛집 홍보 플랫폼에 집행할 수 있다. 혹은 간판 업체에 비용을 지불해 가게 전면·측면·입간판을 다는 것이 가능하다.

웹사이트에서, 이러한 방법 들은 비용이 드는 검색 엔진 마케팅(SEM)과 비슷하다. 이이 광고들은 보통 *Sponsored* 레이블이 붙고, 검색 결과 상단에 노출되는 콘텐츠는 거의 유료다.

그렇다면 어떻게 고깃집은 추가 비용 지불 없이, 기존의 인력과 리소스를 활용해서 마케팅 효과를 얻을 수 있을까?

1. 음식의 맛을 높인다.
노동력과 재료로 반찬과 음식의 맛을 끌어올릴 수 있다. 
2. 주문 부터 식사 까지 과정을 개선한다.
****더 편리한 경험을 제공하기 위해, 불판을 업그레이드 하고, 메뉴 체계를 정돈한다.
3. 특정 고객을 위한 타겟팅을 한다.
이를 테면 가족 단위 손님을 겨냥해 유아용 의자와 식기 등을 마련한다.
4. 친절한 응대로 신뢰도 있는 관계를 쌓는다.
다시 찾고 싶은 가게로 만들고, 손님들이 주변에 추천하도록 한다.

이 고깃집 사례에서 SEO를 떠올릴 수 있다. 

현실에서는 손님이 음식 품질 뿐 아니라, 가게의 명성, 편의성, 평판까지 평가한다. 즉,  **손님 1명은 크롤러와 방문자에 모두 해당**된다. 

Next.js learn에서는 SEO를 다음 3가지로 나누어 설명한다.

### Technical

> “음식의 맛을 높인다.“ 
주문 부터 식사 까지 과정을 개선한다.
> 

해당 방법은 고깃집의 성능을 끌어올리는 작업이다.  즉,  크롤링과 웹 성능을 위해서 웹사이트를 최적화하는 작업에 이치한다.

### Creation

> 특정 고객을 위한 타겟팅을 한다.
> 

이는 웹사이트에서 특정 키워드를 타겟팅하는 콘텐츠 전략과 일치한다.

### Popularity

> 친절한 응대로 신뢰도 있는 관계를 쌓는다.
> 

이는 곧, 손님이 다른 손님을 유치하는 데에 기여한다. 즉, 이는 온라인에서의 백링크와 같다. 제3의 사이트에서 이 웹사이트 좋더라 라고 링크를 걸면 신뢰도가 올라가고, 검색 엔진 역시 더 신뢰 있는 출처로 판단한다.  

물론 순수한 백링크는 구글의 알고리즘으로 구현되어있기에 아래 사항을 주의해야한다.

원래 백링크

= 손님이 진짜 맛있어서 직접 주변에 “여기 추천해!” 라고 말하는 것
→ 100% 무료
→ 가장 강력한 효과

현실에서의 유료 백링크

= 사장이 사람들한테 돈 주고 “우리 가게 맛있다고 말해줘요” 라고 시키는 것
→ 티 나면 신뢰도 떨어지고 오히려 역효과
→ 장기적으로 가게 이미지 망함

이처럼, 원래 백링크의 개념을 구현하기 위해선, **친절하고 맛있는 웹사이트**가 되어야한다.

https://moz.com/learn/seo/backlinks

### 그래서 왜?

고깃집의 사례에서 4가지 방법으로, 다른 고깃집에 비해 방문할 수 있는 우선 순위를 높일 수 있고, 이는 방문자 수를 늘리며,  매출 향상에 실제 기여한다.

SEO 또한, 웹사이트에서 트래픽 향상에 기여하며, 이는 기업에 있어서 아래 3가지를 이유로 중요하다.

- **Qualitative** - 웹사이트 방문자가 실제 고객으로 이어질 가능성이 높아진다.
- **Trustable** –  브랜드, 기업에 대한 신뢰도를 향상 시킨다.
- **Low-Cost** –  기존의 개발 인력, 리소스(시간 등)를 통해 검색 엔진 순위를 높이는 SEO 작업은 무료이다.

# **검색 시스템**

SEO에 대해서 간단히 알아봤으니, SEO에서 SE에 해당되는 검색 시스템, 즉 검색 엔진에 대해서 알아봐야한다. 보통 한국에서의 검색 엔진은 Google, Naver 정도로 생각할 수 있다.

### 주요 역할

그리고 검색 시스템은 4가지의 주요 역할이  있다.

1. 크롤링 
    
    웹을 탐색하고 모든 웹사이트의 콘텐츠를 분석하는 과정 → 3억 6840만 개 (2025년 1분기 말 기준) 가 넘는 도메인이 존재하기 때문에 엄청난 양의 작업이다. 
    
2. 인덱싱
크롤링 단계에서 수집한 모든 데이터를 접근할 수 있도록 저장할 장소를 찾는 작업이다.
3. 렌더링
    
    사이트의 기능 향상, 콘텐츠를 풍부하게 만드는 페이지 리소스를 실행하는 과정 → 물론, 크롤링 되는 모든 페이지에서 수행 되는 것은 아니며, 실제로 콘텐츠가 인덱싱되기 전에 수행되는 경우가 있다. 
    크롤링 시점에 작업을 수행할 리소스가 없는 경우, 인덱싱 후에 렌더링이 수행 될 수 있다.
    
4. 순위
사용자 입력을 기반으로 관련성 높은 결과 페이지를 만들기 위해 데이터를 쿼리하는 작업이다. 검색 엔진에서 다양한 순위 기준을 적용 해서 의도에 맞는 가장 적합한 답변을 제공한다.

웹 크롤러는 마치 사용자 인 것 처럼, 웹사이트에서 찾은 링크를 탐색 → 페이지를 인덱싱 하는 봇이다.

웹 크롤러는 사용자 에이전트를 사용하여 자신을 식별한다. 구글에는 여러개의 웹 크롤러가 있다 하지만 **Googlebot Desktop과 Googlebot Smartphone**이 주로 사용된다.

![image.png](attachment:6d7f62fc-5952-43c7-bee1-40630f862e7e:image.png)

위 그림은 크롤링 과정을 나타낸 다이어그램이다. 과정은 아래와 같다.

1. URL 찾기 
Google은 Google Search Console을 포함해서 여러 곳에서 URL을 수집한다. (웹사이트 간 링크 혹은 XML 사이트맵)
2. 크롤링 대기열에 추가
찾은 URL을 Googlebot이 처리할 수 있게 대기열에 추가한다.
(대부분의 URL은 몇 초 안에 처리되지만, 경우에 따라 며칠 동안 대기할 수도 있다.)
(특히 페이지 렌더링이 필요하거나, 인덱싱하거나, 이미 인덱싱된 URL을 새로 갱신해야 할 때 그렇다.)
그 후 페이지는 렌더링 큐에 추가된다.
3. HTTP 요청
    
    크롤러는 HTTP 요청을 하고 반환된 상태 코드에 따라 작동한다.
    
    - **200:** HTML을 크롤하고 파싱합니다.
    - **30X:** 리디렉션을 따라갑니다.
    - **40X:** 오류를 기록하고 HTML은 불러오지 않습니다.
    - **50X:** 상태 코드가 변경되었는지 나중에 다시 확인할 수 있습니다.
4. 렌더 큐
    
    검색 시스템의 다양한 서비스와 컴포넌트가 HTML을 처리하고 콘텐츠를 파싱
    
    페이지에 클라이언트 사이드 JavaScript 기반 콘텐츠가 있는 경우, 해당 URL은 렌더 큐에 추가될 수 있다.
    
    렌더 큐는 Google이 더 많은 리소스를 사용해야 하므로 비용이 더 들고, 따라서 실제 인터넷에 존재하는 전체 페이지 중에서 렌더링되는 URL의 비율은 상대적으로 적다.
    
    일부 다른 검색 엔진은 Google만큼의 렌더링 능력이 없을 수 있으며, **이 지점에서 Next.js는 렌더링 전략을 보완하는 데 도움을 줄 수 있다.**
    
5. 인덱싱 준비 완료
    
    모든 기준이 충족되면 해당 페이지는 인덱싱될 자격을 갖추게 되고,
    
    검색 결과에 표시될 수 있습니다.

# 크롤러와 인덱싱

검색 시스템과 Googlebot이 작동하는 방법에 대해서 알려면 아래 사항을 알아야한다.

- HTTP 상태 코드의 기본 개념
- 웹 크롤러가 웹 콘텐츠를 파싱할 때 확인하는 메타데이터
- Google의 검색 크롤러가 사이트에 새로운 콘텐츠가 생겼음을 알 수 있도록 소통하는 방법
- 검색 엔진에게 원하는 인덱싱 상태를 알려주기 위해 메타 로봇 태그와 캐노니컬 링크를 활용하는 방법
    - 캐노니컬 태그는 한 페이지를 가리키는 여러 개의 주소가 존재할 때, 검색 엔진의 로봇이 어떤 주소가 원본인지 알 수 있도록 하기 위해 사용하는 태그이다.

### HTTP 상태 코드의 기본 개념

- https://nextjs.org/learn/seo/status-codes

HTTP와 관련해서는 추후 별도 다룰 예정이다. 결론을 말하면 아래와 같다.

| HTTP Status Code | SEO와 관련성 |
| --- | --- |
| 200 | Google에서 페이지가 인덱싱되기 위해서는 반드시 200 상태 코드를 반환해야 한다. |
| 301 / 308 | 리디렉션의 가장 큰 목적은 **URL이 A에서 B로 이동했음을 알리는 것**이다. 콘텐츠가 이동하더라도 현재 및 잠재 고객을 잃지 않도록 하고, 봇이 계속해서 사이트를 인덱싱할 수 있도록 하기 위해 리디렉션이 필요하다. |
| 404 | 404 상태 코드가 무조건 나쁜 것은 아니다.
존재하지 않는 URL을 사용자가 방문했다면 그게 올바른 결과이다.
하지만 사이트 전체에서 잦은 404 발생은 검색 순위 하락으로 이어질 수 있으므로 주의해야 한다. |
| **410** | 이 상태 코드는 자주 사용되지는 않지만, 
더 이상 존재하지 않는 콘텐츠를 사이트에서 삭제할 때 고려할 수 있다.
**HTTP 410을 사용하면 좋은 예**:
**이커머스**: 영구적으로 품절되어 더는 판매하지 않는 제품
**포럼**: 사용자가 삭제한 게시글
**블로그**: 삭제된 블로그 글
**이 상태 코드는 봇에게 이 콘텐츠는 다시는 크롤하지 말라는 신호를 준다.** |
| **503** | 사이트가 다운되어 있고, **오랜 시간 동안 다운될 것으로 예상되는 경우**,
이 상태 코드를 반환하는 것을 추천한다.이렇게 하면 장기적인 검색 순위 하락을 방지할 수 있다. |

## robots.txt 이란?

robots.txt 파일은 크롤러에게 **사이트에서 “어떤 페이지나 파일을 요청할 수 있고, 요청할 수 없는지”** 알려준다. 

robots.txt 파일은 웹 표준 파일이며, 대부분 정상적 봇 들은 특정 도메인에 요청을 보내기 전에 이 파일을 먼저 확인한다. ( 즉, 이전에 웹 크롤러의 과정 1~5 이전에서 작동한다.)

웹사이트의 특정 영역이 크롤링되거나 인덱싱되는 것을 막고 싶을 수 있다. 예를 들어 CMS나 관리자(admin) 페이지, 전자상거래의 사용자 계정, 일부 API 라우트 등이 해당된다.
각 호스트의 루트에서 제공되어야 하며, 또는 루트 경로의 /robots.txt를 다른 URL로 리디렉션해도 대부분의 봇은 이를 따른다.

Next.js에서는 `robots.txt`  파일을 `public`에 추가하면 된다. ( http://localhost:3000/robots.txt 로 접근 할 수 있다)

https://nextjs.org/docs/app/api-reference/file-conventions/metadata/robots 자세한 내용은 해당 글을 참고 할 수 있다.

```
// robots.txt

# Block all crawlers for /accounts  
# → 모든 크롤러가 /accounts 경로를 크롤링하지 못하게 함
```

## XML Sitemap 이란?

사이트맵은 Google과 소통하는 **가장 쉬운 방법** 이다. 사이트맵은 사이트에 속한 URL과 업데이트 시점을 알려주어서 , 새로운 콘테츠를 쉽게 감지할 수 있게 해서 효율적으로 크롤링 할 수 있게 한다.

가장 널리 알려진 사이트맵은 XML 사이트맵이지만, RSS나 Atom을 통해서 생성할 수 있다. 혹은 단순 텍스트 파일로 만들 수 있다.

사이트맵은  사이트의 페이지, 동영상, 기타 파일에 대한 정보와 그들에 대한 관계를 제공하는 파일이다. 구글은 이 사이트맵과 소통하여 지능적으로 사이트를 크롤링한다.

**구글은 아래 경우 사이트맵을 필요로 한다.**

- **큰 사이트 → 새로운 페이지, 콘텐츠 놓칠 가능성 높다.**
- **대량 콘텐츠 아카이브, 서로 연결 부족 → 페이지간 링크가 적어서, 놓칠 가능성 높다.**
- **새로 만들어진 경우 → 링크를 따라가며 페이지를 발견하기에, 외부 링크가 없으면 발견하기 힘들 수 있다.**
- **풍부한 미디어(비디오,이미지)가 많거나 , Google 뉴스에 노출되는 경우 → 사이트맵에 정보를 제공하면 Google이 검색을 위해 추가 정보를 사용할 수 있다.**
    - Google 뉴스에 노출되는 콘텐츠도 풍부한 미디어처럼 추가 메타데이터가 필요하고, 사이트맵을 통해 Google이 더 정확하고 빠르게 처리할 수 있기 때문에 같은 그룹으로 묶여 언급된다.
    - 새로운 콘텐츠가 계속 채워지는 웹사이트라면 **동적 사이트맵을 사용하는 것이 강력히 추천!**
    정적 사이트맵도 유효하지만, Google 입장에서는 항상 최신 콘텐츠를 발견하는 데에는 다소 덜 유용!

### Next.js에서 사용하는 Sitemap

https://nextjs.org/learn/seo/xml-sitemaps 에서는 Page router를 기준으로 설명 되어 있기에, getServerSideProps를 사용했기에, App router 기준으로 학습하기 위해서https://nextjs.org/docs/app/api-reference/file-conventions/metadata/sitemap 도 같이 참고했다.

**1. 정적**

작은 규모의 애플리케이션이면 `sitemap.xml` 파일로 생성해 `app` 디렉토리의 루트에 배치한다.

```xml
<!-- 사이트맵의 최상위 요소. 모든 URL 항목을 감싼다 -->
<urlset xmlns="http://www.sitemaps.org/schemas/sitemap/0.9">

  <!-- 하나의 URL 정보를 담는 블록 -->
  <url>
    <!-- 이 페이지의 실제 URL -->
    <loc>https://acme.com</loc>

    <!-- 이 페이지가 마지막으로 수정된 날짜/시간(ISO 8601 형식) -->
    <lastmod>2023-04-06T15:02:24.021Z</lastmod>

    <!-- 이 페이지가 얼마나 자주 업데이트되는지 검색 엔진에 알려주는 힌트 -->
    <!-- yearly: 1년에 한 번 정도 변경됨 -->
    <changefreq>yearly</changefreq>

    <!-- 해당 URL의 상대적 중요도 (0.0~1.0) -->
    <!-- 홈페이지는 가장 중요하므로 보통 1 -->
    <priority>1</priority>
  </url>

  <url>
    <!-- About 페이지 URL -->
    <loc>https://acme.com/about</loc>

    <!-- 최근 업데이트 날짜 -->
    <lastmod>2023-04-06T15:02:24.021Z</lastmod>

    <!-- monthly: 매달 업데이트될 가능성이 높은 페이지 -->
    <changefreq>monthly</changefreq>

    <!-- 중요도: 홈페이지보다 낮지만 주요 페이지라 0.8 정도 -->
    <priority>0.8</priority>
  </url>

  <url>
    <!-- Blog 목록 페이지 URL -->
    <loc>https://acme.com/blog</loc>

    <!-- 최근 업데이트 날짜 -->
    <lastmod>2023-04-06T15:02:24.021Z</lastmod>

    <!-- weekly: 블로그는 주 단위로 새 글이 올라올 수 있어 변경 빈도가 높음 -->
    <changefreq>weekly</changefreq>

    <!-- 중요도: 0.5는 기본값 수준. 홈페이지나 주요 소개 페이지보다 낮게 설정 -->
    <priority>0.5</priority>
  </url>

</urlset>

```

```xml
    </image:image>

    <!-- 이 페이지가 마지막으로 수정된 날짜 -->
    <lastmod>2021-01-01</lastmod>

    <!-- weekly : 주 1회 정도 업데이트될 수 있다는 의미 -->
    <changefreq>weekly</changefreq>
```

**2. 동적** 

대부분의 애플리케이션에서는 하나의 사이트맵으로 충분하지만, 큰 규모의 웹사이트는 여러 사이트맵으로 분할해야 할 수 있다.

여러 사이트맵을 만드는 방법은 두 가지다.

1. 여러 경로 세그먼트 안에 `sitemap.(xml|js|ts)` 파일을 중첩해 생성
    
    예: `app/sitemap.xml`, `app/products/sitemap.xml`
    
2. [`generateSitemaps`](https://www.notion.so/docs/app/api-reference/functions/generate-sitemaps.md) 함수 사용

예시 (generateSitemaps 사용):

```tsx
import type { MetadataRoute } from 'next'
import { BASE_URL } from '@/app/lib/constants'

export async function generateSitemaps() {
  // 총 상품 수를 확인하고 필요한 sitemap 개수를 계산
  return [{ id: 0 }, { id: 1 }, { id: 2 }, { id: 3 }]
}

export default async function sitemap(props: {
  id: Promise<number>
}): Promise<MetadataRoute.Sitemap> {
  const id = await props.id
  // Google의 한 사이트맵당 50,000 URL 제한
  const start = id * 50000
  const end = start + 50000

  const products = await getProducts(
    `SELECT id, date FROM products WHERE id BETWEEN ${start} AND ${end}`
  )

  return products.map((product) => ({
    url: `${BASE_URL}/product/${product.id}`,
    lastModified: product.date,
  }))
}

```

생성된 사이트맵은 `/product/sitemap/[id]` 형태로 접근 가능.

예: `/product/sitemap/1.xml`

더 자세한 내용은 https://www.notion.so/docs/app/api-reference/functions/generate-sitemaps.md 참고

## 메타 태그

### 검색 엔진을 위한 특수 메타 태그

메타 로봇 태그는 검색 엔진이 항상 존중하는 지시이다. 이러한 메타 로봇 태그를 추가하면 사이트의 인덱싱을 더 쉽게 관리 할 수 있다.

**이때 , 지시와 제안은 차이가 있다.**

- robot tag, robots.txt → 지시됨, 즉 반드시 준수된다.
- canonical 태그 → 검색 엔진이 따를 수도, 무시할 수 도 있는 추천 사항이다.

### noindex,nofollow

```html
<meta name="robots" content="noindex,nofollow" />
```

- 가장 흔한 태그
- noindex : 이 페이지를 검색 결과에 표시하지 말라 → 인덱싱의 여부
- nofollow : 이 페이지에서 발견한 링크를 따라가지 말라 →

```html
<meta name="googlebot" content="noindex,nofollow" />
```

- Googlebot 전용 태그
- 대부분 robots 태그로 충분
- googlebot 태그는 더 Google 전용 규칙이 필요할 때 사용
- 두 태그가 있다면 더 제한적인 것이 적용!

### **질문) robots.txt vs meta robots tag — 왜 둘 다 필요할까?**

- **r**obots.txt로 차단된 URL은 절대 크롤되지 않음
- 하지만 규칙을 나중에 추가하면 이미 인덱싱된 페이지는 제거되지 않을 수 있음
    
    → 인덱싱을 확실하게 막는 가장 좋은 방법은 noindex 메타 태그 즉, **이미 인덱싱된 페이지라도 대부분 검색 결과에서 제거된다.**
    

## **Google 전용 메타 태그**

### **nositelinkssearchbox**

```html
<meta name="google" content="nositelinkssearchbox" />
```

사용자가 브랜드명을 검색하면 Google 검색 결과에 **사이트 전용 검색 박스**가 표시될 때가 있다.

**이 태그는 Google에게 그 검색 박스를 표시하지 말라고 지시한다.** →  사이트에 검색 기능이 없으면 UI가 이상할 수 있다. 그래서 표시하지 말라고 지시한다.

→ 구체적인 사례는 아래와 같다.

1. ‘쿠팡’을 검색 했다.
2. Google에서 바로 내부 검색을 시키게 해줄까? 하는 것이다.

### **notranslate**

```html
<meta name="google" content="notranslate" />
```

Google은 사용자 언어와 다른 언어로 작성된 사이트를 발견하면 자동 번역 링크를 제공한다.

이 메타 태그는 Google에게 **이 페이지를 번역하지 말라**고 알린다.

- 일반적으로는 콘텐츠가 더 많은 사용자에게 보여서 좋지만
- 번역을 원치 않는 상황에서는 이 태그를 사용한다

## Canonical Tags?

canonical URL을 직역하면 표준적인 URL 이다. 사이트 내에서 존재하는 여러 중복 페이지 중에서 
**“이게 가장 대표 URL” 이라고 판된되는 URL이라고 보면된다.**

1. 운영자  —(canoical URL 전달)→  검색 엔진
2. 검색 엔진 — (여러 URL이 같은 페이지다) ⇒ 하나로 묶어 판단.
- 2번도 충분이 잘 처리 된다. 하지만, 워낙 크다면 → 모든 예외 케이스를 다루지 못함
⇒ 그래서 SEO에 있어서 canonical 태그는 매우 중요!
- **만약 중복 콘텐츠를 여러 URL에 가진다 ⇒** 중복 콘텐츠로 검색 순위 낮춘다.
- 같은 콘텐츠를 다른 URL에 게시 ⇒ 한쪽만 순위를 올리거나, 둘다 낮출 수 있다.
- 마케팅 도구가 새로운 URL을 만들 수 있다.
- 검색 엔진이 URL 뒤에서 UTM 파라미터를 추가할 수 있다.

예시

- `jiminseong.com/post/mandalart`
- `jiminseong.com/mandalart`

위 두개가 중복 콘텐츠 라면 

```html
<link rel="canonical" href="https://jiminseong.com/post/mandalart"/>
```

이 또한, App Router 기준으로 명세 되어있어서, 같게 공식 문서를 참고해서 아래와 같이 작성된다.

```tsx
// app/page.tsx
import type { Metadata } from "next";

export const metadata: Metadata = {
  title: "Canonical Example",
  alternates: {
    canonical: "https://example.com",
  },
};

export default function Page() {
  return <p>This page has a canonical tag</p>;
}
```

# 렌더링과 순위

## 렌더링 전략

SEO에서 가장 중요한 것은 데이터와 메타데이터를 JavaScript 없이도 페이지 로드 시 사용할 수 있어야 한다는 것이다. **⇒ SSG 혹은 SSR이 가장 좋은 선택이다!**

(추가로 Next.js 는 페이지 단위로 렌더링 방식을 사용할 수 있다.)

### SSG (Static Site Generation)

- HTML이 빌드 시점에 생성
- HTML이 사전 렌더링 → 페이지 로드 시 모두 준비되어 있음 → 성능 향상에도 도움
- 페이지 성능은 SEO의 또 다른 순위 요소

⇒ SEO 측면에서 아마도 가장 좋은 렌더링 전략 

### SSR (Server-Side Rendering)

- SSG와 마찬가지로 사전 렌더링
- 그러나, HTML이 요청 시점에 생성 (빌드 시점 이후)
- 페이지가 동적인 경우 적합 ex) 실시간 데이터, 요청 시점에 데이터 불러와야하는, 유효 기간이 짧은..

### ISR (Incremental Static Regeneration)

- ‘증분 정적 재생성’ 이라는 뜻, 증분은 ‘증가하는, 증대하는’을 뜻함.
- 페이지 많으면 → 빌드 시점에 생성 불가능
⇒ Next.js에서는 빌드 시점 이후 → 정적 페이지 생성 혹은 업데이트 가능하게 하는 ISR
- 개발자와 콘텐츠 편집자가 전체 사이트를 다시 빌드할 필요 없이, 페이지 단위에서 정적 생성을 사용할 수 있게 한다.

### CSR

- 웹사이트 전체를 브라우저에서 JavaScript로 렌더링
- 초기 로드에는 콘텐츠 거의 없는 HTML 파일 제공
- JavaScript 을 브라우저가 컴파일 한 후 모든게 보임
- SEO에 적합하지 않음
    - 근데 크롤러가 JavaScript가 컴파일되고 읽으면 되지 않나? 
    ⇒ 검색엔진은 먼저 HTML을 보고 판단하는데, CSR은 HTML이 비어 있으므로 렌더 큐로 밀리며, 이 렌더 큐는 비용이 크고 우선순위가 낮아 SEO 품질이 떨어진다.
    
    ⇒ 결론, CSR은 SEO에 좋지 않다.

# URL 구조

URL 구조는 SEO에서 중요하다. 실제로 Google이  SEO에 관한 요소 비율을 공개 하지는 않는다.
그러나 아래의 이유로 깔끔한 URL 구조는 순위 요소에 있어서 중요할 수 있다.

Google이 공식 문서에서 명확히 말한 부분도 있다.

https://developers.google.com/search/docs/crawling-indexing/url-structure?utm_source=chatgpt.com&hl=ko

- URL이 “읽기 쉽고 의미가 있는 구조”라면
    
    → 크롤링 효율상 유리
    
    → 콘텐츠 주제 파악 쉬움
    
    → 사용자 클릭률(CTR) 증가
    
    → 색인(인덱싱) 처리 정확도 증가
    

### 그래서 어떻게?

1. 의미 기반 URL 사용 → 무작위 숫자나 ID 보단 **의미 있는 단어**
ex) jiminseong.com/posts/1 < jiminseong.com/posts/mandal-art-2025
2. 논리적이고 일관도 패턴 → 모든 페이지가 비슷한 규칙을 따르는 것이 좋다.
    
    ex) jiminseong.com/mandal-art-2025 < jiminseong.com/posts/mandal-art-2025
    
3. 키워드 중심 → 구글은 웹사이트의 키워드를 참고한다. → 명확한 키워드로 사용 하자.
4. 파라미터 기반 지양 → 의미가 없어보일 수 있다 or 서로 다른 페이지로 오해할 수 있다.
- Next.js 에서는 폴더 기반 라우팅, 동적 라우팅 으로 적절히 그룹핑을 하여 활용하자

# Metadata

https://nextjs.org/docs/app/getting-started/metadata-and-og-images

메타 데이터는 크게 제목(title), 설명(description), 이미지(OG)가 있다.

### Title

- 가장 중요
- 가장 먼저 보게 되는 요소 이기 때문
- 어떤 내용인지 이해할 때 활용하는 핵심 정보 이기 때문

### Description

- 제목 보단 SEO에 영향력 낮음
- Google에 따르면 직접적으로 순위에 영향을 미치지 않는다.
- 하지만 클릭률(CTR)에 영향을 주기에 매우 중요
- 키워드 포함되어있으면 결과에서 굵게 표시됨

### 적용 예시

1. 정적 
    
    ```tsx
    import type { Metadata } from 'next'
     
    export const metadata: Metadata = {
      title: 'My Blog',
      description: '...',
    }
     
    export default function Layout() {}
    ```
    
2. 동적
    
    ```tsx
    import type { Metadata, ResolvingMetadata } from 'next'
     
    type Props = {
      params: Promise<{ slug: string }>
      searchParams: Promise<{ [key: string]: string | string[] | undefined }>
    }
     
    export async function generateMetadata(
      { params, searchParams }: Props,
      parent: ResolvingMetadata
    ): Promise<Metadata> {
      const slug = (await params).slug
     
      // fetch post information
      const post = await fetch(`https://jiminseong.com/posts/${slug}`).then((res) =>
        res.json()
      )
     
      return {
        title: post.title,
        description: post.description,
      }
    }
     
    export default function Page({ params, searchParams }: Props) {}
    ```

### Structured Data & JSON-LD (구조화된 데이터)

https://nextjs.org/docs/app/guides/json-ld

- 구조화된 데이터는 **검색 엔진이 페이지 내용을 더 정확하게 이해하도록 돕는 정보**
- 대표 표준은 **schema.org**이며, Google, Microsoft, Yahoo 등이 공동으로 사용하는 스키마

**예: 지민성 포스트 페이지에 JSON-LD 스키마 추가하기**

```tsx
 const jsonLd = {
    "@context": "https://schema.org",
    "@type": "BlogPosting",
    headline: post.title,
    description: post.description,
    image: post.thumbnail, // 대표 이미지
    author: {
      "@type": "Person",
      name: "지민성",          // ← 작성자 이름
      url: "https://www.jiminseong.com" // 선택
    },
    datePublished: post.publishedAt,
    dateModified: post.updatedAt ?? post.publishedAt,
    mainEntityOfPage: {
      "@type": "WebPage",
      "@id": `https://www.jiminseong.com/posts/${post.slug}`,
    }
  }

<script
  type="application/ld+json"
  dangerouslySetInnerHTML={{
    __html: JSON.stringify(jsonLd).replace(/</g, '\\u003c')
  }}
/>
```

(XSS 예방을 위해 `<` 를 `\u003c` 로 치환하는 것도 공식 권장 방식)

- **구조화된 데이터(JSON-LD)** →
    
    *검색엔진이 페이지 내용을 깊게 이해하도록 돕는 ‘의미 정보’.*
    
- **Open Graph(OG 태그)** →
    
    *SNS(페이스북·트위터·카톡·텔레그램 등)에서 공유 미리보기를 만드는 정보.*
    
- **사이트맵(XML Sitemap)** →
    
    *검색엔진에게 “내 사이트엔 이런 URL들이 있어!”라고 알려주는 URL 목록.*

# **On Page SEO**

- 페이지 내부에서 SEO에 영향을 주는 요소를 의미한다.
- 헤딩 (H1 ~ ) 과 링크 (link)가 제일 핵심!

## Headings 과 H1

- 검색 엔진은 H1이 가장 중요하다고 여긴다.
- **H1은 각 페이지에 한 번 포함하는 것 이 권장된다.**
- H1은 페이지가 무엇에 관한 것 인지 나타내고, 일반적으로 title과 유사한 내용이 좋다.

## Internal Links

- 백 링크의 역할을 하게되는 것
- 많은 링크를 받은 웹사이트 → 신뢰도가 높은 웹사이트
- PageRank 알고리즘을 이 기반으로 만든다.
    - 각 웹 페이지 모든 링크 분석 → 링크 수(양)/어디서 오는 링크(질)을 기준 → 신뢰도를 점수화
- 권위 있는 도메인에서 링크 받는 것이 매우 가치 큼
- 페이지간 내부 링크, 외부 사이트로의 링크 둘 다 적극적 포함이 필요
- **또한 이를 위해서 href가 반드시 있어야한다.**

### Next.js에서는 Link 컴포넌트를 사용한다.

```tsx
import Link from "next/link";

export default function Page() {
  return (
    <Link href="/about">
      About
    </Link>
  );
}
```

### 유의 사항

- Link의 child가 <a>를 감싼 커스텀 컴포넌트라면, 반드시 passHref(자식으로 전달하라) 를 지정해야한다.
(styled-components, emotion 등 스타일링 라이브러리 사용 시 자주 발생)
- 물론  자식이 `<button>`, `<div>` 같은 NON-a 태그 → 이건 위험
- **a 태그가 아니면 SEO 문제 발생** (App Router에서도 Link children으로 button/div를 넣는 건 비권장)

```tsx
import Link from 'next/link';
import styled from 'styled-components';

// <a> 태그를 감싸는 custom component
const RedLink = styled.a`
  color: red;
`;

function NavLink({ href, name }) {
  // passHref를 반드시 사용해야 함
  return (
    <Link href={href} passHref>
      <RedLink>{name}</RedLink>
    </Link>
  );
}

export default NavLink;

```

# Web Vitals & Core Web Vitals

Web Vitals & Core Web Vitals 에 대해 알아보고 해당 블로그에 대한 조사를 한다.

- Web Vitals, 은 구글이 만든 이니셔티브(구글이 주도해서 만든 공식적인 프로젝트/프로그램이라는 의미) 로, 웹에서 실제 사용자가 경험했을 때 측정되는 가이드 지표를 제공한다.
- Core Web Vitals 은 Web Vitals의 하위 개념
    - 로딩 속도, 인터랙션 반응성, 시각적 안정성을 측정하는 세 가지 핵심 지표로 구성 됨
    - LCP(Largest Contentful Paint), FID(First Input Delay), CLS(Cumulative Layout Shift)
- Core Web Vitals 지표에서 좋은 점수 → 사용자가 더 부드럽고 쾌적한 웹 경험을 제공
- Core Web Vitals 지표가 낮으면 → 검색 순위에 부정적으로 직접적 영향
    - 알고리즘에서 Core Web Vitals 을 검색 순위 판정의 요소로 사용하기 때문
- Core Web Vitals를 측정할 때는 세 가지 평가값이 있다.
    - **Good(좋음) , Needs Improvement(개선 필요), Poor(나쁨)**
- Core Web Vitals를 개선할 때는 두 가지 전략
    1. 가장 높은 점수 → 가능하다면 좋지만, 의존성이 많다면 힘들 수 도.. 
        
        > 구글에서 말하길 “*만족스러운 사용자 경험을 제공하려면 사이트의 점수가 90~100점으로 높아야 합니다. '완벽한' 점수인 100을 달성하기는 매우 어렵고 기대하지 않습니다. 예를 들어 99에서 100 사이의 점수를 가져오려면 90~94가 필요한 것과 거의 동일한 양의 측정항목 개선이 필요합니다.”*
        > 
    2.  경쟁 사이트 보다 높은 점수 → 같은 키워드를 두고 경쟁 

## **Largest Contentful Paint (LCP)**

- Largest Contentful Paint(LCP)는 페이지에서 가장 큰 요소가 로드되어 사용자 화면에 보이는 데 걸리는 시간

[가장 큰 콘텐츠 페인트](https://nextjs.org/_next/image?url=https%3A%2F%2Fh8DxKfmAPhn8O0p3.public.blob.vercel-storage.com%2Flearn%2Fpages-router%2Fseo%2Flcp.png&w=1920&q=75)

- LCP는 페이지의 **로딩 성능**을 측정하는 지표
- 뷰포트 안에서 가장 큰 요소(텍스트 블록, 이미지, 비디오 등)가 화면에 표시되기까지 걸리는 시간
- 이 요소는 보통 페이지에서 가장 중요한 영역을 차지
- FCP와 다름
    - FCP는 페이지 로딩이 시작된 시점부터 **첫 번째 요소가 화면에 표시될 때까지**의 시간
    - DOM이 렌더링되는 동안 페이지에서 “가장 큰 요소”는 계속 바뀔 수 있습니다.
    
    **⇒ LCP는 최종적으로 가장 큰 요소(보통 큰 이미지나 큰 텍스트)가 화면에 보일 때까지 시간을 계속 측정**
    

![image.png](attachment:6b965213-0e8d-4292-9d84-abb55ed77739:image.png)

## **First Input Delay (FID)**

- **2024년 기준 INP로 대체 되었다. 하단에서 설명한다.**
- First Input Delay(FID)는 사용자가 웹 페이지와 상호작용할 때 느끼는 반응성(Responsiveness)을 측정하는 지표
- ex) 입력창을 클릭했는데 아무 반응이 없다면 사용자는 불편함과 답답함을 느끼게 됨
→  이런 **인터랙션 지연**이 바로 FID가 나빠졌다는 신호

[First Input Delay](https://nextjs.org/_next/image?url=https%3A%2F%2Fh8DxKfmAPhn8O0p3.public.blob.vercel-storage.com%2Flearn%2Fpages-router%2Fseo%2Ffid.png&w=1920&q=75)

- FID는 실제 사용자 데이터(필드 데이터)가 필요하며, Google Lighthouse 같은 **랩(Lab) 환경에서는 측정할 수 없다.**
- 대신, Total Blocking Time(TBT)이라는 지표가 있으며, 이는 랩 환경에서 측정 가능하고 **인터랙션에 영향을 주는 문제들을 반영하는 지표이다.**

[First Input Delay Example](https://nextjs.org/_next/image?url=https%3A%2F%2Fh8DxKfmAPhn8O0p3.public.blob.vercel-storage.com%2Flearn%2Fpages-router%2Fseo%2Ffid-example.png&w=3840&q=75)

FID는 브라우저의 메인 스레드가 다른 작업을 처리하느라 바빠서, 사용자의 입력 요청에 즉시 응답하지 못할 때 발생한다.

## **Cumulative Layout Shift (CLS)**

[Cumulative Layout Shift](https://nextjs.org/_next/image?url=https%3A%2F%2Fh8DxKfmAPhn8O0p3.public.blob.vercel-storage.com%2Flearn%2Fpages-router%2Fseo%2Fcls.png&w=1920&q=75)

- Cumulative Layout Shift(CLS)는 웹사이트의 전체적인 레이아웃 안정성을 측정하는 지표
- 페이지가 로딩되는 동안 요소들이 갑자기 움직이거나 위치가 밀리면, 사용자에게 혼란을 주고 잘못된 클릭을 유발 됨.
- CLS는 DOM이 처음 렌더링된 이후, **요소들이 예기치 않게 이동했을 때** 발생
- ex) , 텍스트 블록이 먼저 렌더링된 후 버튼이 늦게 화면에 나타나면서 텍스트가 아래로 밀리는 상황
→  CLS 점수는 다음 두 가지 요소로 계산
    - 얼마나 많이 움직였는가(impact)
    - 얼마나 멀리 이동했는가(distance)

[Cumulative Layout Shift Example](https://nextjs.org/_next/image?url=https%3A%2F%2Fh8DxKfmAPhn8O0p3.public.blob.vercel-storage.com%2Flearn%2Fpages-router%2Fseo%2Fcls-example.png&w=3840&q=75)

새로운 요소가 화면에 렌더링될 때 기존 요소가 **위치가 바뀐다면**, CLS에 영향을 준다.

하지만 다음의 경우에는 CLS로 계산되지 않습니다:

- 새로운 요소가 DOM에 추가되더라도,
- 기존 요소의 크기가 바뀌더라도,
- **기존 요소들의 위치가 그대로 유지된다면** → 레이아웃 이동으로 간주되지 않음.
    - 예: 이미지가 로딩되면서 **위로부터의 위치는 동일**, 크기만 **아래쪽으로 늘어남**.
    
    ```
    [SKELETON RECTANGLE]
    ↓ (이미지 로드)
    [IMAGE]
    (밑으로 늘어남)
    ```
    
    - 위에 있는 요소는 안 움직임.
    - 이미지 자체만 아래로 확장된 것.

## INP

### 2024년, FID →  INP

- 공식 학습 자료 외에 서칭해본 결과
    - https://developers.google.com/search/blog/2023/05/introducing-inp?utm_source=chatgpt.com&hl=ko
    - https://web.dev/blog/inp-cwv?hl=ko
    
    위 두 자료를 통해 새로운 측정항목인 INP는 2024년 3월에 Core Web Vitals의 일부로 FID를 대체한다는 사실을 알 수 있었다.
    
- 대체된 이유는 아래와 같다.
    
    
    | **FID** | 사용자가 “처음으로” 페이지에 상호작용했을 때 브라우저의 첫 반응 속도 |
    | --- | --- |
    | **INP(현재)** | 페이지 전체에서 일어나는 상호작용의 반응성 |

![inp-desktop-v2.svg](attachment:252a7ef4-cc6b-4ae8-a64b-6f8ab1729c49:inp-desktop-v2.svg)

- Core Web Vitals 개선을 위한 지침을 따르고 있는 사용자라면 이미 페이지의 응답성을 고려
- 즉, 기존에 작업했던 FID 개선은 INP와 페이지의 응답성을 개선하기 위한 좋은 기초
- 최적화 가이드 : https://web.dev/articles/optimize-inp?hl=ko
