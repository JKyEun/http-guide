# 20장: 리다이렉션과 부하 균형

리다이렉션은 HTTP 메시지의 최종 목적지를 정하는 방법으로, 프락시/캐시/서버 팜 같은 구성에서 요청을 어디에서 처리할지 결정해서 다른 곳으로 보낼 수 있음.

## 20-1 왜 리다이렉트인가?

HTTP 애플리케이션은 신뢰할 수 있는 트랜잭션 수행과 지연 최소화, 네트워크 대역폭 절약을 목표로 함.

주요 목표:
- 신뢰할 수 있는 HTTP 트랜잭션 수행
- 지연 최소화
- 네트워크 대역폭 절약

이를 위해 웹 콘텐츠를 여러 위치에 분산시키며, 이점은 아래와 같음:

- **신뢰성 향상**: 한 위치가 실패해도 대체 위치를 사용 가능함
- **응답 시간 단축**: 클라이언트가 가까운 리소스에 접근 가능함
- **네트워크 혼잡 감소**: 분산된 목적지 서버로 인해 부하가 분산됨

리다이렉션과 부하 균형은 같이 움직이는 경우가 많으며, 보통 리다이렉션 장치가 부하 균형까지 같이 처리함.

## 20-2 리다이렉트 할 곳

리다이렉션 대상:
- 클라이언트 입장에서는 서버/프락시/캐시/게이트웨이 모두 HTTP 요청을 받아 처리하는 대상임
- 리다이렉션 기법 대부분은 전반적으로 적용됨
- 다만 일부는 특정 엔드포인트에만 맞는 경우도 있음

## 20-3 리다이렉션 프로토콜의 개요

리다이렉션 목표:
- HTTP 메시지를 가능한 한 빠르게 응답할 수 있는 웹 서버로 보내는 것
- 실제로 어디로 가는지는 애플리케이션/라우팅 장치 설정에 따라 달라질 수 있음

리다이렉션이 발생하는 메커니즘:

- **브라우저 애플리케이션 설정**: 사용자가 브라우저를 설정하여 클라이언트 메시지를 프락시 서버로 보냄
- **DNS 리졸버**: 메시지 주소를 지정할 때 사용할 IP 주소를 선택하며, 클라이언트의 지리적 위치에 따라 달라질 수 있음
- **네트워크 스위치와 라우터**: 메시지는 여러 패킷으로 나뉘어 네트워크를 통과하며, 스위치와 라우터는 패킷의 TCP/IP 주소를 확인하고 라우팅을 결정함
- **웹 서버 HTTP 리다이렉트**: 웹 서버가 HTTP 리다이렉트를 사용하여 요청을 다른 웹 서버로 보냄

적용 범위:
- DNS 리다이렉션 같은 방법은 목적지가 서버든 캐시든 크게 상관없이 쓸 수 있음
- 반대로 브라우저 설정은 프락시로 보내는 경우에만 해당됨

## 20-4 일반적인 리다이렉션 방법

### 20-4-1 HTTP 리다이렉션

동작 방식:
- 웹 서버가 리다이렉트 응답을 보내서, 클라이언트가 다른 서버로 다시 요청하게 만들 수 있음
- 간단한 부하 균형을 할 때도 이 방식을 쓰며, 리다이렉팅 서버가 부하가 적은 콘텐츠 서버를 골라서 보냄

흐름 예시:

1. 클라이언트가 www.joes-hardware.com에 /hammers.html 요청을 보냄
2. 서버가 302 리다이렉트 응답을 보내며 Location: http://161.58.228.45/hammers.html 헤더를 포함함
3. 브라우저가 자동으로 리다이렉트를 따라 161.58.228.45로 새 요청을 보냄

단점:

- 원 서버가 어디로 보낼지 결정해야 해서, 경우에 따라 처리 부담이 커질 수 있음
- 페이지 접근에 왕복이 한 번 더 생김: 초기 요청 → 리다이렉트 서버, 리다이렉트된 요청 → 목적지 서버
- 리다이렉트 서버가 실패하면 전체 사이트도 실패함
- 이런 단점 때문에 HTTP 리다이렉션은 보통 다른 리다이렉션 기법과 같이 사용됨

### 20-4-2 DNS 리다이렉션

DNS 리다이렉션 기본:
- 웹사이트에 접근하려면 도메인명을 IP 주소로 바꿔야 하고, 이 작업을 DNS 분석자가 처리함
- 클라이언트 OS, 로컬 DNS, 원격 DNS 등이 resolver 역할을 함
- DNS는 한 도메인에 여러 IP를 붙일 수 있고, 어떤 IP를 돌려줄지 결정하는 방법도 다양함

DNS 라운드 로빈:
- 가장 흔하고 단순한 방식으로, DNS 서버가 룩업할 때마다 IP 목록 순서를 돌려서 부하를 분산함
- 보통 클라이언트는 여러 IP 중 첫 번째 주소로 접속함

예시:
- 앨리스가 www.cnn.com을 조회하면 첫 번째 IP로 207.25.71.5를 받아 접속함
- 다음에 밥이 조회하면 목록이 한 번 순환돼 207.25.71.6을 받아 접속함

DNS 캐싱 영향:
- DNS 결과는 앱/운영체제/로컬 DNS에 캐시될 수 있어서, 한 클라이언트는 한동안 같은 서버만 계속 쓰는 경우가 많음
- 대신 비슷한 요청을 하는 클라이언트가 충분히 많으면 전체 부하는 서버들로 비교적 잘 분산됨

다른 DNS 기반 알고리즘:
- 부하 균형: 서버 부하를 추적해서 덜 바쁜 서버를 우선함
- 근접 라우팅: 지리적으로 가까운 서버로 보내려 함
- 결함 마스킹: 네트워크 상태를 보고 장애/실패를 피해서 라우팅함
- 이런 결정을 하는 DNS는 콘텐츠 제공자가 운영하는 권위 있는 DNS인 경우가 많음
- 다만 결정에 쓰는 정보가 클라이언트 IP가 아니라 로컬 DNS 서버 IP인 경우가 많아서 한계가 있음

### 20-4-3 임의 캐스트 어드레싱

동작 방식:
- 여러 서버가 같은 IP를 공유하게 해서, 요청이 가장 가까운 서버로 가게 만드는 방식이며 라우터의 최단 경로 라우팅에 의존함
- 서버가 자기 주변 라우터에 "이 IP는 내가 처리할 수 있음"을 광고함
- 라우터는 그 IP로 들어온 패킷을 가장 가까운 광고 지점(서버)으로 보냄

예시:
- 세 서버가 모두 10.10.10.1을 쓰고, LA/NY 서버가 각 지역 라우터에 광고함
- 클라이언트 요청은 자동으로 가장 가까운 서버로 라우팅됨

제약:
- 실험적인 기법이고, 서버가 라우팅 프로토콜 쪽과 연동되어야 하는 경우가 있음
- “IP 하나 = 서버 하나”라는 일반 가정과 충돌할 수 있어서, 주소 충돌/라우팅 누수 같은 문제가 생길 수 있음

### 20-4-4 아이피 맥 포워딩

이 방식은 스위치가 MAC 주소(레이어 2)를 기준으로 트래픽을 프락시/서버 쪽으로 넘기는 방식임.

- 레이어-2 스위치: MAC 기준으로 패킷을 전달함
- 레이어-4 인식 스위치: IP/포트까지 보고 분기할 수 있음. 포트 80 트래픽만 프락시 캐시로 보내는 식임
- 프락시 캐시: 캐시에 있으면 바로 응답하고, 없으면 원 서버로 요청을 대신 보냄

제약:
- MAC 포워딩은 점대점이라 서버/프락시가 스위치에서 한 홉 거리 안에 있어야 함

### 20-4-5 아이피 주소 포워딩

특징:
- 목적지 MAC이 아니라 목적지 IP를 바꿔서 트래픽을 프락시/서버로 보내며, 보통 NAT로도 부름
- MAC 포워딩과 비교하면, 목적지 서버가 스위치 한 홉 거리일 필요는 없음
- 대신 응답도 같은 스위치로 돌아와야 하는 라우팅 대칭성 문제가 생김

응답 경로를 잡는 방법:
1. 완전 NAT: 출발지 IP까지 스위치 IP로 바꿔서 응답이 항상 스위치로 돌아오게 함. 대신 서버는 클라이언트 원 IP를 못 보고, 인증/결제 등에 영향이 있음
2. 반 NAT: 출발지 IP는 클라이언트 IP로 유지함. 대신 서버→클라이언트가 스위치를 우회하는 직접 경로가 없어야 함. 서버는 클라이언트 IP를 볼 수 있지만 네트워크 제어가 필요함

### 20-4-6 네트워크 구성요소 제어 프로토콜

네트워크 구성요소 제어 프로토콜(NECP)은 라우터/스위치 같은 네트워크 장치(NE)와 웹 서버/프락시 캐시 같은 서버 장치(SE)가 통신해서, 요청 처리를 네트워크 단에서 제어할 수 있게 해주는 프로토콜.

주요 기능:
- SE가 NE에 부하 균형 정보를 제공해서 NE가 그 기준대로 트래픽을 분산하게 함
- MAC 포워딩, GRE 캡슐화, NAT 같은 포워딩 방식을 지원하며 WCCP와 유사함
- 예외 처리도 지원하여 특정 출발지 IP나 목적지/프로토콜/포트를 원 서버로 보내는 식으로 우회 가능함

NECP 메시지:

| 메시지 | 누가 보내는가 | 의미 |
| --- | --- | --- |
| NECP_NOOP | - | 작업 없음 - 아무 일도 하지 않음 |
| NECP_INIT | SE | SE가 NE와의 통신을 개시함. SE는 NE와의 TCP 커넥션을 연 뒤 이 메시지를 NE에게 보냄. SE는 반드시 연결할 NE 포트를 알아야 함 |
| NECP_INIT_ACK | NE | NECP_INIT를 받았음을 알림 |
| NECP_KEEPALIVE | NE 혹은 SE | 피어가 살아있는지 물어봄 |
| NECP_KEEPALIVE_ACK | NE 혹은 SE | keep-alive 메시지에 대답함 |
| NECP_START | SE | SE는 "나는 여기에 있고 네트워크 트래픽을 받을 준비가 되어 있다"고 말함. 포트를 지정할 수 있음 |
| NECP_START_ACK | NE | NECP_START를 받았음을 알림 |
| NECP_STOP | SE | SE는 NE에게 "트래픽을 나에게 보내는 것을 중단하라"라고 말함 |
| NECP_STOP_ACK | NE | NE는 정지를 알림 |
| NECP_EXCEPTION_ADD | SE | SE는 NE의 목록에 하나 이상의 예외를 추가하라고 말함. 예외는 출발지 아이피, 목적지 아이피, 프로토콜 혹은 포트에 근거할 수 있음 |
| NECP_EXCEPTION_ADD_ACK | NE | EXCEPTION_ADD의 확인 |
| NECP_EXCEPTION_DEL | SE | NE에게 하나 이상의 예외를 그의 목록에서 삭제하라고 요청함 |
| NECP_EXCEPTION_DEL_ACK | NE | EXCEPTION_DEL을 승인함 |
| NECP_EXCEPTION_RESET | SE | NE에게 예외 목록 전체를 삭제하라고 요청함 |
| NECP_EXCEPTION_RESET_ACK | NE | EXCEPTION_RESET을 승인함 |
| NECP_EXCEPTION_QUERY | SE | NE 전체의 예외 목록을 문의함 |
| NECP_EXCEPTION_RESP | NE | 예외 문의에 대해 답함 |

## 20-5 프락시 리다이렉션 방법

프락시 사용 이유:
- 콘텐츠에 접근할 때 보안상의 이유로 프락시를 쓰는 경우가 많음
- 로컬 프락시 캐시 이점 때문에 사용하기도 함

### 20-5-1 명시적 브라우저 설정

동작 방식:
- 브라우저에서 프락시 서버 IP/포트를 직접 지정하는 방식이며, 한 번 설정하면 모든 요청이 지정된 프락시로 감
- 일부 서비스 제공자는 프락시 주소가 미리 들어간 브라우저를 배포하기도 함

단점:

- 프락시가 응답하지 않아도 브라우저가 프락시를 사용하도록 설정되어 있으면 원 서버에 연락하지 않음. 프락시가 다운되거나 잘못 구성되면 사용자는 연결 문제를 경험함.
- 네트워크 아키텍처 변경(예: 프락시 추가/제거)을 모든 최종 사용자에게 전파하기 어려움. 사용자는 브라우저의 프락시 설정을 수동으로 변경해야 함.

### 20-5-2 프락시 자동 설정

PAC 개요:
- 명시적 설정은 사용자가 일일이 바꿔야 해서, 네트워크 구조가 바뀔 때 대응이 느림
- 브라우저가 자동으로 올바른 프락시를 고르게 하는 방식이 필요함
- 프락시 자동 설정은 보통 PAC로 처리하며, 넷스케이프가 정의했고 대부분의 주요 브라우저가 지원함
- 기본 아이디어는 브라우저가 PAC 파일을 가져와서 URL마다 어떤 프락시를 쓸지 결정하는 것임

PAC 파일은 자바스크립트 파일이며 아래 함수를 정의해야 함:

```javascript
function FindProxyForURL(url, host)
```

브라우저는 요청된 모든 URL에 대해 이 FindProxyForURL 함수를 호출하며, URL과 호스트를 인자로 전달함:

```javascript
return_value = FindProxyForURL(url_of_request, host_in_url);
```

PAC 특징:
- 반환 값은 브라우저가 URL을 어디로 보낼지 지정하는 문자열이며, 연락할 프락시 목록이나 DIRECT를 지정할 수 있음
- DIRECT를 받으면 프락시를 우회하고 원 서버로 직접 요청함
- 자바스크립트로 DNS, 서브넷, 요일/시간 같은 조건을 보고 프락시를 동적으로 고를 수 있음
- 프락시 위치가 바뀌면 PAC 파일만 업데이트하면 되므로 네트워크 변경 대응이 쉬워짐

### 20-5-3 웹 프락시 자동발견 프로토콜

WPAD 개요:
- PAC 파일 URL을 자동으로 찾는 프로토콜임
- PAC 파일을 찾으면 실행해서 이 요청은 어떤 프락시로 보낼지를 결정함

발견 순서:
1. DHCP
2. SLP
3. DNS에게 잘 알려진 호스트명
4. DNS SRV 레코드
5. TXT 레코드의 DNS 서비스 URL

필수:
- 위 5개 중 DHCP와 DNS well-known hostname만 필수로 구현되어 있음

동작 흐름:
- 지원하는 발견 기법을 순서대로 시도함
- 성공하면 PAC 후보 URL(CURL)을 만들고, 그 URL로 PAC 파일을 가져옴
- 끝까지 못 찾으면 WPAD 실패, 클라이언트는 프락시를 쓰지 않도록 구성됨

DHCP 기반:
- DHCP 서버에 PAC URL을 넣어둠(보통 DHCP 옵션 코드 252)

DNS A 레코드 기반:
- DNS에 wpad 호스트명으로 A 레코드가 있어야 함
- 예: QNAME=wpad.TGTDOM., QCLASS=IN, QTYPE=A

PAC 파일 가져오기:
- 후보 URL로 GET을 보냄
- Accept: application/x-ns-proxy-autoconfig 같은 헤더를 포함해야 함
- 결과가 리다이렉트면 최종 목적지가 클라이언트의 대상이 됨

WPAD 실행 시점:
- 웹 클라이언트 시작 시(첫 인스턴스만 발견, 이후 인스턴스는 설정 상속)
- 클라이언트 IP 주소가 바뀔 때
- PAC 파일이 만료될 때
- PAC가 대안을 못 주거나 현재 프락시가 실패할 때
- PAC를 무효화했을 때. 참고로 WPAD는 PAC에 대한 If-Modified-Since 조건부 요청을 지원하지 않음

주의사항:
- 브로드캐스트/멀티캐스트 왕복이 여러 번 생길 수 있어서 너무 자주 돌리면 부담됨

보안(WPAD 스푸핑):
- wpad를 붙여서 wpad.a.b.microsoft.com → wpad.b.microsoft.com → wpad.microsoft.com처럼 단계적으로 탐색할 수 있음
- 악성 WPAD 서버로 트래픽이 리다이렉트되거나 가로채질 수 있음

타임아웃:
- 각 단계를 보통 10초 안쪽으로 제한함(네트워크 상황에 따라 조정 가능)

관리자 고려사항:
- 클라이언트 호환성 때문에 DHCP와 DNS A 레코드 기반을 반드시 준비해야 함
- DHCP/DNS를 먼저 맞춰두면 클라이언트 시작 시간이 줄어듦

근접성 판단에 쓸 수 있는 요소는 다음과 같음:
- DHCP 서버는 서브넷, cipaddr, 식별자 옵션을 기준으로 판단함
- DNS 서버는 도메인 접미사에 따라 SRV/A/TXT 응답을 다르게 줄 수 있음
- PAC URL을 다루는 웹 서버는 User-Agent, Accept, 클라이언트 IP/서브넷/호스트명, 주변 프락시 배치 등을 기준으로 판단 가능함
- PAC 파일은 클라이언트가 여러 대안 중 실시간 선택이 가능할 정도로 표현력이 있음

## 20-6 캐시 리다이렉션 방법

개요:
- 캐싱 프락시 서버를 위한 리다이렉션 기법들임
- 신뢰성/성능을 높이고 콘텐츠가 있을 만한 곳으로 보내는 동작까지 포함하는 경우가 많음

### 20-6-1 WCCP 리다이렉션

WCCP 개요:
- 라우터가 웹 트래픽을 프락시 캐시로 리다이렉트할 수 있게 해주는 프로토콜임
- 라우터와 캐시 통신으로 캐시가 살아있는지, 어디로 보낼지를 관리함

WCCP 리다이렉션 동작:
- 통신 가능한 네트워크가 필요함
- 라우터와 캐시 묶음이 서비스 그룹을 만들고, “어떤 트래픽을 어디로 보낼지/어떻게 분산할지”를 정함
- 라우터는 HTTP 요청을 서비스 그룹의 캐시로 리다이렉트함
- 라우터는 캐시를 하나 선택한 다음, 캡슐화나 MAC 포워딩으로 캐시에 전달함
- 캐시가 처리를 못 하면 패킷이 라우터로 돌아갈 수 있음
- 서비스 그룹은 하트비트 메시지로 가용성을 계속 확인함

WCCP2 메시지:

| 메시지 이름 | 누가 보내는가 | 전달하는 정보 |
| --- | --- | --- |
| WCCP2_HERE_I_AM | 캐시가 라우터에게 | 캐시가 트래픽을 받을 수 있다고 라우터에게 알림. 캐시의 모든 서비스 그룹 정보를 포함함. 캐시가 서비스 그룹에 가입할 때 즉시 그룹의 모든 라우터에게 이 메시지를 보냄. 이 메시지는 라우터에게 WCCP2_I_SEE_YOU 메시지를 보내 협상을 시작함 |
| WCCP2_I_SEE_YOU | 라우터가 캐시에게 | WCCP2_HERE_I_AM에 대한 응답. 패킷 포워딩 방법, 할당 방법(지정된 캐시가 누구인지), 패킷 반환 방법, 보안을 협상하는 데 사용됨 |
| WCCP2_REDIRECT_ASSIGN | 지정된 캐시가 라우터에게 | 부하 균형을 위한 할당을 수행함. 해시 테이블 부하 균형 또는 마스크/값 부하 분산을 위한 버킷 정보 또는 마스크/값 페어링 정보를 보냄 |
| WCCP2_REMOVAL_QUERY | 라우터가 2.5×HERE_I_AM_T초 동안 WCCP2_HERE_I_AM 메시지를 보내지 않은 캐시에게 | 라우터가 일정 기간(2.5×HERE_I_AM_T초) 동안 정기적으로 WCCP2_HERE_I_AM 메시지를 받지 못하면, 라우터는 이 메시지를 보내 캐시가 서비스 그룹에서 제거되어야 하는지 문의함. 캐시의 올바른 응답은 HERE_I_AM_T/10초 간격으로 동일한 WCCP2_HERE_I_AM 메시지 세 개를 보내는 것임 |



WCCP2 메시지 구성요소:

| 구성요소 | 설명 |
| --- | --- |
| 보안 정보 | 보안 옵션과 그 구현을 포함함. 보안 옵션은 WCCP2_NO_SECURITY (0) 또는 WCCP2_MD5_SECURITY (1)임. WCCP2_NO_SECURITY가 선택되면 보안 구현 필드가 없음. WCCP2_MD5_SECURITY가 선택되면 보안 구현 필드는 메시지 체크섬과 서비스 그룹 비밀번호를 포함하는 16바이트 필드임. 비밀번호 길이는 최대 8바이트임 |
| 서비스 정보 | 서비스 그룹을 설명함. 서비스 유형 ID는 WCCP2_SERVICE_STANDARD (0) 또는 WCCP2_SERVICE_DYNAMIC (1)일 수 있음. 서비스 유형이 WCCP2_SERVICE_STANDARD이면 서비스 ID로 정의된 잘 알려진 서비스임(예: HTTP는 알려진 표준 서비스). 서비스 유형이 WCCP2_SERVICE_DYNAMIC이면 서비스는 후속 우선순위, 프로토콜, 서비스 플래그(해싱 결정), 포트 설정으로 정의됨 |
| 라우터 식별 정보 | 라우터의 IP 주소와 ID를 포함하며, 라우터가 통신하려는 모든 웹 캐시를 IP 주소 순으로 나열함 |
| 웹 캐시 식별정보 | 웹 캐시의 IP 주소와 리다이렉션 해시 테이블 매핑을 포함함 |
| 라우터 뷰 정보 | 라우터의 서비스 그룹 관점(라우터와 캐시의 식별자)을 포함함 |
| 웹 캐시 뷰 정보 | 웹 캐시의 서비스 그룹 관점을 포함함 |
| 할당 정보 | 특정 해싱 버킷에 대한 웹 캐시의 할당을 보여줌 |
| 라우터 질의 정보 | 라우터의 IP 주소, 질의된 웹 캐시의 IP 주소, 서비스 그룹의 웹 캐시로부터 WCCP2_HERE_I_AM 메시지를 받은 마지막 라우터의 ID를 포함함 |
| 능력 정보 | 라우터가 지원하는 패킷 포워딩, 부하 균형, 패킷 반환 방법을 광고하는 데 사용됨. 또한 웹 캐시가 라우터에게 선호하는 방법을 알리는 데 사용됨 |
| 대체 할당 | 부하 균형을 위한 해시 테이블 할당 정보를 포함함 |
| 할당 맵 | 서비스 그룹에 대한 마스크/값 집합 요소를 포함함 |
| 명령 확장 | 캐시가 라우터에게 중지했음을 알리는 데 사용됨. 또한 라우터가 캐시가 중지했음을 승인하는 데 사용됨 |


- 서비스 그룹은 WCCP를 지원하는 라우터와 캐시 묶음이며, 라우터가 웹 트래픽을 그룹 내 캐시로 보냄. 구성 정보는 Here I Am, I See You 같은 메시지로 교환됨
- GRE 패킷 캡슐화는 라우터가 HTTP 패킷을 특정 서버 IP로 캡슐화해서 전달하는 방식이며, IP 헤더 proto 필드로 캡슐화 여부를 나타냄. 이 방식은 클라이언트의 원래 IP 주소가 손실되지 않음
- WCCP 부하 균형은 라우터와 수신 서버가 하트비트로 상태를 공유하며, 특정 노드가 죽으면 그 노드 대신 인터넷으로 직접 보내고 복구되면 다시 그 노드로 보냄

## 20-7 인터넷 캐시 프로토콜

ICP 개요:
- 근처 캐시에게 URL 존재 여부를 물어봐서 HTTP 요청을 어디로 보낼지 결정하는 프로토콜이며, 리다이렉션 프로토콜로도 분류됨
- 질의하는 캐시가 인접 캐시에 ICP 요청을 보내고, 인접 캐시는 HIT이나 MISS로 응답함
- HIT면 그 캐시와 HTTP 연결을 열어서 객체를 가져올 수 있음
- 단순하고 가벼우며, 메시지는 네트워크 바이트 순서와 32비트 정렬이라 파싱이 쉬움
- 전송은 UDP를 쓰는 경우가 많아서 손실을 감지하려면 타임아웃 처리가 필요함

ICP 메시지 구성요소:

| 필드 | 설명 |
| --- | --- |
| OP 코드(8비트) | 메시지 종류. 기본 질의는 ICP_OP_QUERY, 응답은 ICP_OP_HIT/ICP_OP_MISS |
| 버전(8비트) | ICP 버전. 예: Squid는 ICPv2 사용, RFC 2186에 정리되어 있음 |
| 메시지 길이(16비트) | 전체 길이. 최대 16,383바이트까지 가능 |
| 요청 번호 | 동시 요청/응답을 구분하는 번호. 응답은 요청과 같은 번호를 포함해야 함 |
| 옵션(32비트) | 동작을 바꾸는 플래그 비트. 예: ICP_FLAG_HIT_OBJ, ICP_FLAG_SRC_RTT |
| 옵션 데이터(32비트) | 옵션용 예약 영역. ICPv2에선 하위 16비트에 RTT 측정값을 담기도 함(선택) |
| 발송자 호스트 주소(32비트) | 발송자 IP. 역사적인 이유로 남아 있지만 실제로는 잘 쓰지 않음 |
| 페이로드 | 메시지 유형에 따라 달라짐. ICP_OP_QUERY: 요청자 호스트 주소 + NUL 종료 URL / ICP_OP_HIT_OBJ: NUL 종료 URL + 16비트 객체 크기 + 객체 데이터 |

## 20-8 캐시 배열 라우팅 프로토콜

CARP 개요:
- ICP의 대안이며, 여러 프락시 서버를 써서 성능을 올리려는 목적은 같음
- URL을 특정 프락시에 결정론적으로 매핑해서, 한 번의 계산으로 "이 객체는 어디에 있을지"를 바로 결정할 수 있음

CARP 리다이렉션:
- 참여하는 프락시 서버 테이블을 유지함(살아있는지 확인하려고 주기적으로 폴링됨)
- 각 프락시 서버에 대해 “부하 용량”을 반영한 해시 값을 계산함
- 요청 URL을 기반으로 별도의 해시 값을 계산함
- URL 해시 + 서버 해시를 합쳐 값 배열을 만들고, 최대값이 나온 프락시 서버를 선택함
- 위 계산은 브라우저나 중간 서버에서 수행될 수도 있음
- 프락시 서버 그룹은 서버 목록 테이블을 만들고, 부하 요소/TTL/폴링 주기 같은 정보를 포함할 수 있음
- 테이블은 RPC로 원격 관리될 수 있고, 업데이트는 HTTP로 배포될 수 있음(클라이언트/프락시는 잘 알려진 URL에서 가져옴)
- 해시 함수는 객체가 전체 서버에 걸쳐 정적으로 분산되게 해야 하고, 부하 요소는 할당 확률에 영향을 줌

장점:
- 결정론적이라 형제 캐시에 계속 질의하는 트래픽이 줄어듦
단점:
- 프락시 한 대가 장애가 발생하면 해시를 다시 맞춰야 하고 콘텐츠 재배치 비용이 커질 수 있음
- 새로운 프로토콜이라 ICP 전용 프락시가 CARP 무리에 쉽게 포함되기 어려움

## 20-9 하이퍼텍스트 캐싱 프로토콜

HTCP 개요:
- 형제들이 URI와 모든 요청 및 응답 헤더를 사용해서 서로 문서 존재 여부를 질의할 수 있게 해줌
- 이 덕분에 적중이 아닌데도 적중으로 잘못 처리될 확률이 줄어듦
- 형제 캐시 안에 있는 선택된 문서의 추가/삭제를 모니터링하고 요청할 수 있음
- 서로의 캐시된 문서에 대한 캐싱 정책 변경을 요청할 수 있음

트랜잭션 흐름:
- ICP와 유사하며, 근처 캐시가 그 문서를 갖고 있으면 요청 캐시는 그 캐시에 HTTP 커넥션을 열고 문서를 가져옴
- ICP와 HTCP 트랜잭션은 요청/응답의 상세함 정도가 다름

HTCP 메시지 구조:
- 헤더, 데이터, 인증으로 구성됨
- 헤더 영역은 32비트 메시지 길이, 8비트 주 프로토콜 버전, 8비트 부 프로토콜 버전으로 이뤄져 있음
- 메시지 길이는 모든 헤더와 데이터, 인증 크기를 포함함

데이터 구성요소:

| 구성요소 | 설명 |
| --- | --- |
| 데이터 길이 | 데이터 영역 크기의 16비트 값. 길이 필드의 길이 자체도 포함함 |
| OP 코드 | HTCP 트랜잭션을 위한 4비트 명령 코드. OP 코드의 전체 목록은 아래 OP 코드 표에 제공되어 있음 |
| 응답 코드 | 트랜잭션의 성공이나 실패를 가리키는 4비트 값. 가능한 값: 0(인증은 사용되지 않았지만 필요함), 1(인증이 사용되었지만 만족되지 않았음), 2(구현되지 않은 OP 코드), 3(지원되지 않는 주 버전), 4(지원되지 않는 부 버전), 5(부적절하거나 허용되지 않거나 바람직하지 않은 OP 코드) |
| F1 | F1은 과적재되어 있음. 메시지가 요청이면 "응답이 필요함"(F1=1)을 알려주는 요청자 플래그 집합이고, 메시지가 응답이면 "전체 메시지에 대한 응답"(F1=1)인지 "OP 코드 데이터 필드에 대한 응답"(F1=0)인지 알려주는 비트 플래그임 |
| RR | 메시지가 요청인지(RR=0) 응답인지(RR=1) 알려주는 1비트 플래그임 |
| 트랜잭션 아이디 | 요청자의 네트워크 주소와 결합되어 HTCP 트랜잭션을 유일하게 식별하는 32비트 값임 |
| OP 코드 데이터 | OP 코드 데이터는 OP 코드에 의존함 |

HTCP OP 코드:

| Opcode | 값 | 설명 | 응답 코드 | OP 코드 데이터 |
| --- | ---: | --- | --- | --- |
| NOP | 0 | 일종의 ping과 같은 작업 | 항상 0 | 없음 |
| TST | 1 | 엔터티 존재 여부 테스트 | 만약 엔터티가 존재한다면 0, 엔터티가 존재하지 않는다면 1 | 요청의 URI와 요청 헤더, 그리고 응답의 응답 헤더를 포함함 |
| MON | 2 | 모니터링 | 받아들이면 0, 거절하면 1 | - |
| SET | 3 | 캐시가 캐싱 정책의 변경을 요청할 수 있게 해줌 | 받아들이면 0, 무시하면 1 | - |
| CLR | 4 | 캐시 삭제 | 갖고 있었지만 이젠 없다면 0, 갖고 있었고 지금도 그렇다면 1, 갖고 있지 않았다면 2 | - |

### 20-9-1 HTCP 인증

HTCP 메시지의 인증 부분은 선택적임.

인증 구성요소:

| 구성요소 | 설명 |
| --- | --- |
| 인증 길이 | 메시지의 인증 영역이 몇 바이트인지 담고 있는 16비트 숫자임. 이 길이는 길이 필드 자체의 길이도 포함함 |
| Sig 시간 | 서명이 생성된 시각을 세계 표준시(GMT) 1970년 1월 1일 이후로 경과한 초 단위의 시간으로 표현한 32비트 숫자임 |
| Sig 만료 | 서명이 만료될 시각을 세계 표준시(GMT) 1970년 1월 1일 이후로 경과한 초 단위의 시간으로 표현한 32비트 숫자임 |
| 키 값 | 공유된 비밀(shared secret)의 이름을 담은 문자열임. 키 영역은 두 부분으로 나뉨: 이어지는 문자열이 몇 바이트인지 표현한 16비트 길이값 + 문자열의 연속 바이트 스트림 |
| 서명 | 출발지/목적지 IP 주소와 포트, 메시지 주/부 HTCP 버전, Sig 시간/Sig 만료 값, 전체 HTCP 데이터, 키에 대한 HMAC-MD5 요약으로 만든 값임. 이 서명도 16비트 길이값 + 서명 바이트 스트림, 이렇게 두 부분으로 되어 있음 |

### 20-9-2 캐싱 정책 설정

SET 메시지는 캐시가 캐시된 문서에 대한 정책 변경을 요청할 수 있게 함.

캐싱 정책 변경에 쓰는 헤더:

| 헤더 | 설명 |
| --- | --- |
| Cache-Vary | 요청자는 콘텐츠가 응답 Vary 헤더의 집합과 다른 헤더의 집합에 따라 달라진다는 것을 배웠음. 이 헤더는 응답 Vary 헤더를 덮어씀 |
| Cache-Location | 프락시 캐시의 목록은 객체의 사본을 가질 수도 있음 |
| Cache-Policy | 요청자는 이 객체에 대한 캐싱 정책을 응답 헤더에 명시된 것보다 더 자세하게 배웠음. 가능한 값: no-cache(응답이 캐시 가능하지만 동시에 여러 요청자들 사이에서 공유될 수 있음을 의미), no-share(공유할 수 없는 객체), no-cache-cookie(콘텐츠는 쿠키와 캐싱 결과에 따라 변할 수 있으므로 권하지 않음) |
| Cache-Flags | 요청자는 객체의 캐싱 정책을 수정했으며, 따라서 객체는 특별히 취급되어야 할 수도 있음(그러나 객체의 실제 정책에 꼭 부합해야 할 필요는 없음) |
| Cache-Expiry | 요청자가 알게 된 문서의 실제 만료 일시 |
| Cache-MD5 | 요청자가 계산한 그 객체의 MD5 체크섬으로, Content-MD5 헤더의 값과 다를 수 있으며, 그 객체가 Content-MD5 헤더를 갖고 있지 않기 때문에 제공된 것일 수도 있음 |
| Cache-to-Origin | 요청자가 측정한 원 서버로의 왕복 시간. 이 헤더 값의 형식: <원 서버 이름 혹은 아이피> <평균 왕복 시간(초 단위)> <샘플의 개수> <요청자와 원 서버 사이의 라우터 홉 개수> |

요청과 응답 헤더를 질의 메시지에 담아 형제 캐시로 보내는 것이 허용됨에 따라, HTCP는 캐시 질의에서 거짓 적중의 비율을 줄일 수 있음. 더 나아가 HTCP는 형제 캐시들이 정책 정보를 서로 교환할 수 있게 함으로써 그들이 더욱 서로를 잘 도울 수 있도록 해줄 수 있음.


# 21장: 로깅과 사용 추적

## 21-1 로그란 무엇인가?

로깅 목적:
- 서버나 프락시의 문제를 찾기 위해
- 웹사이트 접근 통계를 내기 위해

기록 항목:
- 트랜잭션의 모든 헤더를 기록할 수도 있지만 너무 많아서, 보통 기본 항목만 남김
- 주로 HTTP 메서드, 클라이언트/서버 버전, 요청 URL, 응답 상태 코드, 요청/응답 크기, 트랜잭션 시간, Referer, User-Agent 값을 기록함

## 21-2 로그 포맷

로그 포맷 개요:
- 로그 포맷은 여러 가지가 있음
- 대부분의 서버/프락시는 표준 포맷을 지원함
- 표준 포맷을 쓰면 로그 분석 도구로 통계/분석하기 편함

### 21-2-1 일반 로그 포맷

개요:
- NCSA가 정의했으며, 많은 서버에서 기본값으로 사용함
- 상용/오픈 소스 서버 모두 설정해서 사용할 수 있음

| 필드 | 설명 |
| --- | --- |
| remotehost | 요청한 컴퓨터의 호스트명 또는 IP 주소 |
| username | ident 룩업이 수행되었다면 인증된 사용자의 이름 |
| auth-username | 인증이 수행되었다면 인증된 사용자의 이름 |
| timestamp | 요청의 날짜와 시간 |
| request-line | HTTP 요청 라인 그대로. 예: "GET /index.html HTTP/1.1" |
| response-code | 응답에서 보낸 HTTP 상태 코드 |
| response-size | 응답 엔터티의 Content-Length. 응답에 엔터티가 반환되지 않으면 값은 0 |

예시:
```
209.1.32.44 - - [03/Oct/1999:14:16:00 -0400] "GET / HTTP/1.0" 200 1024
http-guide.com - dg [03/Oct/1999:14:16:32 -0400] "GET / HTTP/1.0" 200 477
http-guide.com - dg [03/Oct/1999:14:16:32 -0400] "GET /foo HTTP/1.0" 404 0
```

### 21-2-2 혼합 로그 포맷

혼합 로그 포맷은 일반 로그 포맷에 Referer, User-Agent 두 필드가 추가된 형태이며, Apache 같은 서버에서 많이 사용함.

| 필드 | 설명 |
| --- | --- |
| Referer | Referer HTTP 헤더의 값 |
| User-Agent | User-Agent HTTP 헤더의 값 |

예시:
```
209.1.32.44 - - [03/Oct/1999:14:16:00 -0400] "GET / HTTP/1.0" 200 1024 "http://www.joes-hardware.com/" "5.0: Mozilla/4.0 (compatible; MSIE 5.0; Windows 98)"
```



### 21-2-3 넷스케이프 확장 로그 포맷

넷스케이프 확장 로그 포맷은 일반 로그 포맷을 기반으로 하며, 프락시/캐시 환경을 위해 필드를 더 붙인 형태임.

| 필드 | 설명 |
| --- | --- |
| proxy-response-code | 트랜잭션이 프락시를 거칠 경우, 서버에서 프락시로의 HTTP 응답 코드 |
| proxy-response-size | 트랜잭션이 프락시를 거칠 경우, 서버가 프락시에 전달하는 응답 엔터티의 Content-Length |
| client-request-size | 클라이언트가 프락시로 보내는 요청의 본문이나 엔터티의 Content-Length |
| proxy-request-size | 트랜잭션이 프락시를 거칠 경우, 프락시가 서버로 보내는 요청의 본문이나 엔터티의 Content-Length |
| client-request-hdr-size | 클라이언트 요청 헤더의 바이트 길이 |
| proxy-response-hdr-size | 트랜잭션이 프락시를 거칠 경우, 프락시가 요청자에게 보내는 응답 헤더의 바이트 길이 |
| proxy-request-hdr-size | 트랜잭션이 프락시를 거칠 경우, 프락시가 서버로 전송하는 요청 헤더의 바이트 길이 |
| server-response-hdr-size | 서버 응답 헤더의 바이트 길이 |
| proxy-timestamp | 트랜잭션이 프락시를 거칠 경우, 요청과 응답이 프락시를 통해 오가는 총 시간(초 단위) |



예시:
```
209.1.32.44 - - [03/Oct/1999:14:16:00-0400] "GET / HTTP/1.0" 200 1024 200 1024 0 0 215 260 279 254 3
```

### 21-2-4 넷스케이프 확장 2로그 포맷

넷스케이프 확장 2로그 포맷은 넷스케이프 확장 로그 포맷에서 필드를 더 확장한 형태이며, 프락시/캐시 환경에서 더 많은 정보를 남기기 위한 용도임.


| 필드 | 설명 |
| --- | --- |
| route | 프락시가 클라이언트를 대신하여 요청을 할 때 사용하는 경로 |
| client-finish-status-code | 클라이언트 종료 상태 코드 |
| proxy-finish-status-code | 프락시 종료 상태 코드 |
| cache-result-code | 캐시 결과 코드 |


예시:
```
209.1.32.44 - - [03/Oct/1999:14:16:00-0400] "GET / HTTP/1.0" 200 1024 200 1024 0 0 215 260 279 254 3 DIRECT FIN FIN WRITTEN
```

route 코드:

| 값 | 설명 |
| --- | --- |
| DIRECT | 리소스를 서버에서 바로 가져왔음 |
| PROXY(host:port) | 리소스를 host라는 프락시를 통해 가져왔음 |
| SOCKS(socks:port) | 리소스를 host라는 SOCKS 서버를 통해 가져왔음 |

종료 상태 코드:

| 값 | 설명 |
| --- | --- |
| - | 요청이 시작되지 않았음 |
| FIN | 요청이 성공적으로 완료되었음 |
| INTR | 요청이 클라이언트에 의해 중단됐거나 프락시/서버에 의해 종료되었음 |
| TIMEOUT | 요청이 프락시/서버의 타임아웃에 걸렸음 |

캐시 코드:

| 코드 | 설명 |
| --- | --- |
| - | 캐시할 수 없는 리소스임 |
| WRITTEN | 리소스를 캐시에 저장했음 |
| REFRESHED | 리소스를 캐시했고 갱신했음 |
| NO-CHECK | 캐시된 리소스를 반환했고 신선도 검사를 하지 않았음 |
| UP-TO-DATE | 캐시된 리소스를 반환했고 신선도 검사를 완료했음 |
| HOST-NOT-AVAILABLE | 캐시된 리소스를 반환했으며 원격 서버가 사용할 수 있는 상태가 아니었기 때문에 신선도 검사를 하지 않았음 |
| CL-MISMATCH | 리소스를 캐시에 저장하지 않았음. Content-Length가 리소스의 크기와 맞지 않았기 때문에 쓰기를 중단했음 |
| ERROR | 어떤 에러 때문에 리소스를 캐시에 저장하지 못했음. 예를 들면 타임아웃이 나거나 클라이언트가 트랜잭션을 중단했을 때 |

유연한 로그 포맷:
- 넷스케이프는 유연한 로그 포맷을 사용해서 관리자가 필요한 필드만 골라 기록할 수 있음
- 어떤 정보가 필요할지 미리 예측하기 어렵기 때문에, 다른 프락시/서버도 비슷하게 로그에서 필요한 정보만 추출하는 기능을 제공하는 경우도 있음

### 21-2-5 스퀴드(Squid) 프락시 로그 포맷

개요:
- 오픈 소스 프락시/캐시 서버임
- 로그 포맷을 그대로 쓰거나 참고하는 경우가 많음

| 필드 | 설명 |
| --- | --- |
| timestamp | 요청이 도착한 시간으로, GMT 1970년 1월 1일 이후 경과한 초 단위로 표현됨 |
| time-elapsed | 요청과 응답이 프락시를 통해 이동하는 데 걸린 총 시간(밀리초 단위) |
| host-ip | 클라이언트(요청자) 호스트 장치의 IP 주소 |
| result-code/status | result 필드는 프락시가 요청에 대해 무엇을 했는지 스퀴드 포맷으로 설명함. code 필드는 프락시가 클라이언트에게 보낸 HTTP 응답 코드임 |
| size | 프락시가 클라이언트에게 보낸 응답의 길이로, HTTP 응답 헤더와 본문을 포함하며 바이트 단위임 |
| method | 클라이언트 요청의 HTTP 메서드임 |
| url | 클라이언트 요청의 URL임 |
| rfc931-ident | 클라이언트의 인증된 사용자명임 |
| hierarchy/from | 넷스케이프 포맷의 route 필드와 유사하게, hierarchy 필드는 요청이 프락시를 통해 이동한 경로를 설명함. from 필드는 프락시가 요청을 만들게 한 서버의 이름을 설명함 |
| content-type | 프락시 응답 엔터티의 Content-Type임 |

예시:
```
99823414 3001 209.1.32.44 TCP_MISS/200 4087 GET http://www.joes-hardware.com - DIRECT/proxy.com text/html
```

스퀴드 결과 코드:
| 결과 코드 | 의미 |
| --- | --- |
| TCP_HIT | 캐시에서 유효한 복제본을 전달 |
| TCP_MISS | 캐시에 없어 원 서버에서 가져옴 |
| TCP_REFRESH_HIT | 재검사 후 캐시를 전달 |
| TCP_REF_FAIL_HIT | 재검사에 실패해서 신선하지 않은 복제본을 전달 |
| TCP_REFRESH_MISS | 재검사 결과 만료로 판단되어 새 버전을 가져옴 |
| TCP_CLIENT_REFRESH_MISS | 요청자가 Pragma: no-cache나 Cache-Control 지시자를 보내서 강제로 다시 가져옴 |
| TCP_IMS_HIT | 캐시된 복제본에 대해 조건부 요청으로 재검사를 요청함 |
| TCP_SWAPFAIL_MISS | 캐시에 있다고 봤지만 어떤 이유로 접근하지 못함 |
| TCP_NEGATIVE_HIT | 캐시된 에러 응답을 전달함. 예: 404 Not Found |
| TCP_MEM_HIT | 메모리 캐시에서 유효한 복제본을 전달 |
| TCP_DENIED | 권한 문제 등으로 요청이 거부됨 |
| TCP_OFFLINE_HIT | 오프라인 상태에서 캐시된 복제본을 전달 |
| UDP_* | 요청이 UDP 인터페이스로 프락시에 도착했음을 의미 |
| UDP_HIT | 캐시에서 유효한 복제본을 전달 |
| UDP_MISS | 캐시에 없음 |
| UDP_DENIED | 요청이 거부됨 |
| UDP_INVALID | 요청 자체에 문제가 있음 |
| UDP_MISS_NOFETCH | 미스 응답만 반환하고 리소스는 가져오지 않음 |
| NONE | 보통 에러와 함께 기록됨 |
| TCP_CLIENT_REFRESH | TCP_CLIENT_REFRESH_MISS를 참조 |
| TCP_SWAPFAIL | TCP_SWAPFAIL_MISS를 참조 |
| UDP_RELOADING | UDP_MISS_NOFETCH를 참조 |

## 21-3 적중 계량하기

개요:
- 캐시 때문에 서버 로그가 비는 문제를 보완하기 위해 나온 아이디어임

### 21-3-1 개요

캐시 로그 문제:
- 원 서버 로그는 결산/통계를 낼 때 많이 사용되며, 콘텐츠 접근 빈도나 광고 노출, 페이지 인기 같은 것을 추적함
- 그런데 중간에 캐시가 있으면 많은 요청이 원 서버까지 가지 않아서 원 서버 로그에 누락이 발생함
- 그래서 특정 콘텐츠는 캐시를 못 쓰게 막아서 요청이 원 서버로 가게 만들기도 함

적중 계량 해법:
- 캐시 파기 없이 하려면 캐시 쪽에서 얼마나 제공했는지를 서버가 알 수 있어야 함
- HTTP 확장으로 적중 계량 규약이 나왔고, 캐시가 접근 통계를 원 서버에 주기적으로 보고하게 됨
- 완벽한 해법은 아니고 널리 쓰이진 않지만, 캐시 성능은 살리면서 통계는 받는 방향이라 캐시 파기 대신 고려할 만한 선택지가 됨

### 21-3-2 Meter 헤더

개요:
- 적중 계량 확장은 Meter라는 헤더를 추가함
- 캐시/서버는 이 헤더에 사용량 보고나 사용 제한 같은 지시자를 넣어 주고받을 수 있음

적중 계량 지시자:

| 지시자 | 주체 | 설명 |
| --- | --- | --- |
| will-report-and-limit (w) | 캐시 | 캐시는 사용량을 보고하고 서버가 정한 모든 사용 제한을 따름 |
| wont-report (x) | 캐시 | 캐시는 사용 제한은 따르지만, 사용량을 보고하지 않음 |
| wont-limit (y) | 캐시 | 캐시는 사용량 보고는 하지만, 사용 제한은 없음 |
| count (c) | 캐시 | "사용 횟수/재사용 횟수" 형식으로 정수를 기술하는 보고 지시자임(예: ":count=2/4"). 적중 계량에서 '재사용 횟수'는 클라이언트 요청을 다시 검증한 횟수를 의미하며, '사용 횟수'는 요청에 응답한 횟수를 의미함 |
| max-uses (u) | 서버 | 서버가 캐시를 사용해서 응답할 수 있는 최대 횟수를 지정함(예: "max-uses=100") |
| max-reuses (r) | 서버 | 서버가 캐시를 재사용하여 응답할 수 있는 최대 횟수를 지정함(예: "max-reuses=100") |
| do-report (d) | 서버 | 서버가 프락시에게 사용량 보고를 요청함 |
| dont-report (e) | 서버 | 서버가 사용량 보고를 원하지 않음 |
| timeout (t) | 서버 | 서버가 리소스 계량 시 시간 제한을 두는 데 사용함. 캐시는 지정된 타임아웃 시간 정각이나 1분 전후로 보고를 전송해야 함(예: "timeout=60") |
| wont-ask (n) | 서버 | 서버는 계량 정보를 원하지 않음 |

예시 흐름은 다음과 같음:
- 트랜잭션은 클라이언트와 프락시 캐시 사이의 일반적인 HTTP 트랜잭션처럼 시작됨
- 프락시의 요청과 서버의 응답에 Meter 헤더가 추가되어 있음
- 프락시는 서버에게 적중 계량을 수행할 수 있음을 알림
- 서버는 프락시에게 적중 횟수 보고를 요청함
- 클라이언트 입장에서는 요청이 평소처럼 처리되고, 프락시는 서버 리소스에 대한 추적을 시작함
- 이후 프락시는 재검사를 위한 조건부 요청에 추적 정보를 담아 보내고 적중 횟수를 함께 보고함

## 21-4 개인 정보 보호에 대해

로깅의 특성:
- 서버/프락시의 관리 기능이고, 거의 모든 HTTP 트랜잭션에 적용될 수 있음
- 사용자는 본인 트랜잭션이 로깅되는 걸 모를 수도 있고, HTTP를 쓰고 있다는 사실조차 모르는 경우도 있음

개인 정보 위험:
- 로그에는 사용자에 대한 정보가 많이 쌓일 수 있고, 차별/희롱/갈취 같은 나쁜 목적으로 악용될 위험이 있음
- 로그를 남기는 쪽은 개인 정보 보호를 신경 써야 함

주의사항:
- 감시되고 있다는 사실은 명확히 공지해야 함
- 인지/허가 없이 하는 로깅은 사생활 침해가 될 수 있음
- 개발자/운영자는 이런 로깅이 상황에 따라 불법이 될 수도 있다는 점도 유념해야 함
