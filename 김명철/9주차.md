# 18장: 웹 호스팅

- 콘텐츠 리소스를 저장, 중개, 관리하는 일을 통칭하는 말
- 학습목표
  1. 가상호스팅 하는 방법과 그것이 HTTP에 끼치는 영향
  2. 트래픽이 많은 상황에서 안정적인 사이트를 구축하는 법
  3. 웹 사이트 로딩을 빠르게 하는 법

## 1. 가상 호스팅과 HTTP

- 초기: 각 회사가 자체 하드웨어, 네트워크, 소프트웨어를 구축 관리함.
- 문제: 구축, 관리 할 수 있는 역량을 갖추기 어렵다.
- 해결: 물리적인 관리부터 콘텐츠 제공까지하는 총체적인 웹 호스팅 서비스 등장.

### 1-1 전용 호스팅

\*\* ISP(Internet Service Provider): 인터넷 서비스 제공자 (SKT, KT, LGU+ 같은 회사들)

- ISP가 제공하는 웹 서버를 임대한다.
- HTTP로 각각의 다른 IP 주소로 요청을 하게 된다.

### 1-2 가상 호스팅

- 전용 호스팅은 너무 비싸다. 반면 웹 서버를 보유하고 싶은 수요는 많다.
- 가상 호스팅은 물리적으로는 하나인 컴퓨터를 공유하여 여러 서비스를 호스팅하게 해준다.
  - end-user 입장에서 전용 호스팅과 구분되지 않는다.
  - 비용, 관리적 효율성이 높다.

#### HTTP 1.0의 한계

- URL에서 path만 전송한다.
- 호스트를 식별하는 기능을 제공하지 않는다.
- 서로 다른 두 웹 서버에 (같은 호스팅) `GET /index.html`을 요청해도 구분 불가
- 1.1에서는 URL 전체를 전송하게 하여 해결했다.

#### 1.0의 호스트 구분 해결 방법들

1. URL 경로

- 일반적으로 좋지 않다. (/index.html을 생략하는 등의 디폴트 동작이 작동하기 어려움)

2. 포트번호

- 포트번호 모른채로 쓸 수가 없다

3. IP 주소

- 각 서버마다 IP 주소 할당
- URL -> IP -> TCP연결 -> HTTP 통신
- 한 컴퓨터에 연결할 수 있는 IP 갯수가 제한적 (몇개? 왜 제한적?)
- 서버 복제되는 경우 그만큼 IP도 더 필요하게 됨
- IP 자체가 희소적임 (갯수가 제한되어 있음 - 몇개?)

4. Host 헤더

- HTTP1.0+에서 첫 소개, 1.1에서는 필수이다.
- `Host = "Host" ":"호스트[ ":"포트 ]`
- Host 헤더 기술을 필수다
- 반드시 원 서버의 호스트 명과 포트를 기술해야 한다.
- 전체 URL이 요청에 기술되어 있으면 Host 헤더는 무시하고 URL을 사용한다.

## 2. 안정적인 사이트

- 장애상황 세가지
  1. 서버 다운
  2. 트래픽 폭증
  3. 네트워크 장애 및 손실

### 해결방법1: 미러링된 서버 팜

- 서버팜
  > 서로 대신할 수 있고 식별할 수 있게 설정된 웹 서버들의 집합
- 미러링된 서버는 마스터 원 서버와 동일하게 행동한다.
- 간단한 배포: 네트워크 스위치를 사용하여 분산 요청 보내기
  - 콘텐츠는 스위치의 IP를 가리킨다.
- 분산된 미러링 서버
  - 클라이언트 요청이 적절한 곳으로 가도록 한다
    - HTTP 리다이렉션: 마스터 서버가 복제서버로 리다이렉트 시킴
    - DNS 리다이렉션: 설명이 더 필요해~~

### 해결방법2: CDN

- CDN(Content Delivery Network): 특정 콘텐츠의 분산을 목적으로 하는 단순한 네크워크
- 서버들의 분산된 네트워크이며, 각 노드들은 서버, 대리서버, 프락시서버가 된다.

```
[클라이언트] ←→ [포워드 프락시] ←→ [리버스 프락시/CDN] ←→ [원본 서버]
```

#### CDN 대리 캐시

- 대리서버: 리버스 프락시라고도 불린다
- 콘텐츠에 대한 요청을 대신 받는다.
- 수요에 따라 동작한다.
- 클라이언트가 요청하는 콘텐츠만 저장한다.
- 콘텐츠 미리 가져오기 기능을 가지기도 한다.

#### CDN 프락시 캐시

- 요청이 있을 때만 저장한다.
- 스위치, 라우터가 중간 웹 트래픽을 가로채 처리하기도 한다.
- 콘텐츠는 받는 요청에 따라서 캐시에 분산된다.

### 요약

| 구분      | 미러링된 서버팜            | CDN                            |
| --------- | -------------------------- | ------------------------------ |
| 저장 내용 | 원본 전체 복제             | 요청된 콘텐츠만 캐시           |
| 동기화    | 서버 간 데이터 동기화 필요 | 캐시 만료되면 원본에 다시 요청 |
| 비용      | 높음 (전체 복제)           | 낮음 (필요한 것만)             |
| 독립성    | 원본 없어도 동작 가능      | 원본 서버 필요                 |

## 3. 빠르게 로딩하기

- 핵심: 클라이언트와 서버 사이에서 인터넷을 통해 빠르게 데이터를 전송하는 것
- 서버팜, CDN으로 혼잡제어, 트래픽 분산
- 압축을 통해 전송데이터량을 줄이기

## 현대의 웹호스팅 모습

첫째, 클라우드 인프라가 기본이 됐어요. AWS, GCP, Azure 같은 서비스에서 필요한 만큼만 서버를 빌려 쓰고, 트래픽이 늘면 몇 분 안에 자동으로 서버가 늘어나요 (오토스케일링).
둘째, 서버리스와 컨테이너가 등장했어요. 서버 관리 자체를 안 해도 되는 서버리스(AWS Lambda 등)나, 애플리케이션을 컨테이너(Docker, Kubernetes)로 패키징해서 어디서든 동일하게 실행할 수 있게 됐죠.
셋째, 비용 구조가 완전히 바뀌었어요. 초기 투자 비용 없이 사용한 만큼만 지불하는 종량제가 표준이 됐어요.
넷째, 글로벌 배포가 쉬워졌어요. 과거 CDN은 정적 파일 위주였다면, 이제는 엣지 컴퓨팅으로 서버 로직 자체를 전 세계 곳곳에서 실행할 수 있어요 (Cloudflare Workers, Vercel Edge Functions 등).

# 19장: 배포 시스템

FrontPage, WebDAV 모두 사양된 기술이므로
그에 대해서 자세히 학습하지 않겠습니다.

## FrontPage Server Extensions (FPSE)

- Microsoft FrontPage 전용 서버 확장
- HTTP POST 위에 독자적 RPC 프로토콜 구현
- \_vti_bin 등 특수 경로로 파일 관리
- 비표준, Microsoft 전용

## WebDAV

- HTTP/1.1 확장한 IETF 공식 표준
- PROPFIND, MKCOL, COPY, MOVE, LOCK 등 새 HTTP 메서드 추가
- 웹 서버를 원격 파일 시스템처럼 사용 가능

## 현재 상황

- FPSE: 2003년경 지원 중단, 보안 문제로 완전히 퇴출
- WebDAV: macOS Finder, NAS, CalDAV/CardDAV 등에서 제한적 사용
- 웹 배포 용도로는 둘 다 사실상 사장됨
- Git, CI/CD, 클라우드 API, 컨테이너 배포로 대체

### Git

- 기존 한계: 파일 단위 덮어쓰기, 변경 이력 없음, 협업 시 충돌 관리 불가
- 극복 방식:
  - 모든 변경 이력 추적 및 버전 관리
  - 브랜치로 병렬 작업, 머지로 충돌 해결
  - 롤백, 코드 리뷰, 책임 추적 가능

### CI/CD

- 기존 한계: 수동 빌드/테스트/배포, 휴먼 에러, 느린 배포 주기
- 극복 방식:
  - 코드 푸시 시 자동 빌드·테스트·배포
  - 일관된 품질 검증 파이프라인
  - 하루에도 수십 번 안전하게 배포 가능

### 클라우드 API

- 기존 한계: 서버에 직접 파일 업로드, 서버 구성 수동 관리
- 극복 방식:
  - 인프라를 코드로 프로비저닝 (IaC)
  - 스토리지, DB, 서버를 API 호출로 즉시 생성/삭제
  - 확장성, 자동화, 멀티 리전 배포 용이

### 컨테이너 배포

- 기존 한계: "내 PC에선 되는데" 문제, 환경 불일치, 의존성 충돌
- 극복 방식:
  - 앱 + 환경을 이미지로 패키징해 어디서든 동일 실행
  - 빠른 스케일링, 오케스트레이션(Kubernetes)
  - 개발·스테이징·프로덕션 환경 완전 일치
